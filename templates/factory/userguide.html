Software Factory User Guide

How to ship features with /factory: a spec, a build, four reviewers, a triage step and an approver, all driven by markdown files.

Command names. The factory ships as the software-factory plugin, so commands are namespaced: /software-factory:factory ... and /software-factory:init. Everywhere this guide writes /factory, use the namespaced form if the short one is not recognized.

The idea

You describe a feature in one line. The factory turns it into a written spec, builds it on its own git branch, has independent reviewers check it, and either merges it or hands it to you with a clear question. You keep the decisions that need judgment; the factory handles the rest.

  • Files, not chat. Every agent reads its context from files and writes exactly one file. Nothing depends on a conversation staying alive.
  • One writer of state. Only the /factory session writes factory/board.json, so the dashboard never sees half-written state.
  • Process fits the size of the work. Small changes use the quick track; larger ones use full.
  • You stay in control. Anything uncertain becomes needs-human; nothing risky merges silently.
  • It grills before it guesses. When the factory needs decisions (a raw vision, or a spec with open questions) it interviews you with the bundled grill skill until nothing is left assumed. Questions come in numbered rounds. Routine ones ([recommend]) carry a suggested answer; product-defining ones ([open]) do not, so the call is yours. You can also run /software-factory:grill <topic> on any idea.

The four skills

SkillUse it whenWhat you get
/software-factory:initOnce per project, and again after each plugin update to upgrade the project. It is safe to re-run.factory/, the project-context block in CLAUDE.md, your test command (for existing code), and, if you say yes, permission for the factory to merge approved jobs

/software-factory:brainstorm [topic]The idea is still vague, and you need options before decisionsMany ideas, all yours (the coach adds none), narrowed with MoSCoW into docs/intent.md
/software-factory:grill [topic]You have a direction, plan or spec and want it stress-testedSettled decisions D1, D2, … in docs/grill-log.md and docs/intent.md

Brainstorm widens; grill narrows. Brainstorm asks one open prompt at a time and works through techniques such as What If, Worst Idea and Role Playing. It narrows the result only at the end, using your own judgments. Grill asks every question it can ask now, numbered, and waits for your answers before the next round. It looks up facts itself and asks you only for decisions. When the idea is vague, run brainstorm and then grill. Both keep a log, so an interrupted session resumes where it stopped. Both end by showing your answers back before adding their own observations.

The factory also runs them for you. factory plan brainstorms a thin vision, then always grills it unless you say "skip grill". factory plan <capability> on an existing product does the same for one feature, logging in docs/features/<slug>/. factory document grills you on why the code is the way it is. A job whose spec has open decisions grills you before any code is written. In an unattended factory run, nothing grills mid-job: the question is parked in factory/inbox.md, and the run offers to grill you through the inbox at the end.

Which workflow do I follow?

Where you areFollow
I only have an idea or a vision statementWorkflow A: start from an idea
I have a very vague idea (a sentence or two)Workflow A; brainstorming runs first automatically
I have working code and want to add featuresWorkflow B: existing implementation
I have code and a big new capability (more than a few jobs)Workflow B: plan the capability with /factory plan <capability>

Workflow A: start from an idea

1 Init→ 2 Plan (3 passes)→ 3 Scaffold job→ 4 Feature loop→ 5 Retro
  1. Init. Create an empty folder, open Claude Code in it and run: 
    > /software-factory:init
    It creates the git repo (branch main) and records default_branch, factory/, and a project-context block in CLAUDE.md with <TBD> for the test command. That is expected for now.
  2. Plan. Give the factory your idea in your own words: 
    > /software-factory:factory plan A tool that helps small SaaS teams get SOC 2 ready
  faster by collecting evidence automatically and tracking controls.
    • Pass 1, Clarify. If the idea is thin, you are brainstormed first (the coach asks, you generate, then MoSCoW narrows). Then you are grilled in rounds. Answer every question; [open] ones have no suggested answer on purpose. You approve docs/vision.md and docs/product-brief.md.
    • Pass 2, Architecture. The planner proposes the stack as numbered decisions (docs/decisions.md) and a pre-mortem listing how the product most likely fails. Push back on anything: your note re-runs the pass. You approve.
    • Pass 3, Epics and backlog. You get epics with "done when" checks and an ordered factory/backlog.md. You approve, then approve the proposed CLAUDE.md block (stack, test command, conventions). Nothing is built yet.
  3. Scaffold job. Backlog item 1 is always the project skeleton with a passing test, documented commands and CI: 
    > /software-factory:factory next
    It may run without a test command, because its acceptance criteria create one. After it merges, every later job has a real baseline.
  4. Feature loop. Repeat /software-factory:factory next for each backlog item. Keep the dashboard open. When a card turns amber (needs-human), read its decision.md or answer its questions, then approve or rework. Anything beyond the plan goes in with /software-factory:factory <feature> or as a new - [ ] line in backlog.md.
  5. Retro. When an epic's last item merges, the factory reports which of its "done when" checks hold. Run /software-factory:factory retro now and then (it is offered every 5 finished jobs); approve the lessons you want added to CLAUDE.md.
Tip. Commit after each approved planning pass. The docs/ files are the product's memory; every later agent reads them.

Workflow B: you already have an implementation

1 Init in the repo→ 2 Context + document→ 3 Plan a capability→ 4 Run→ 5 Retro
  1. Prepare the repo. Commit or stash your code changes (jobs need no uncommitted changes outside factory/, docs/ and CLAUDE.md). Be on your default branch (any name: main, master, develop…). init detects it and records it as default_branch in factory/board.json; jobs branch from it and merge back into it. Nothing is renamed. If your default branch is protected or needs pull requests, the factory pushes the job branch and asks you to open a PR instead of merging.
  2. Init. In the repo root: 
    > /software-factory:init
    It adds factory/ and appends the project-context block to your existing CLAUDE.md (nothing is overwritten). Because code exists, it also looks for your test, lint and build commands, runs the tests once, and shows you the exact lines it proposes to write. Approve them, and accept init's offer to commit (a job will not start while its .gitignore change is uncommitted).
  3. Confirm context. Open CLAUDE.md and add only what an agent cannot learn from the code: policy, frozen or generated paths, non-default conventions, and mistakes you have actually seen. Skip directory trees and tech-stack lists. You do not plan the whole product.
  4. Document what exists. Run: 
    > /software-factory:factory document
    The planner reads your manifests, config, entrypoints, data models, CI and git history, then drafts docs/architecture.md and docs/decisions.md. Every decision is marked Status: inferred and cites the files or commits it came from. Where the code cannot tell the planner why, it writes "Context: unknown" and you are grilled on those questions (why this datastore, which parts are legacy, which conventions are law). Answered decisions become accepted. You approve the result, and the proposed CLAUDE.md facts, before anything is saved. Expect a few minutes of questions; this is what stops later specs from contradicting your past choices. Accept the commit it offers. You do this once per repo.
  5. Plan a capability. (After the documentation is approved.) 
    > /software-factory:factory plan let customers invite teammates and revoke access
    With the architecture on record, plan runs in feature mode: three approved passes for this one capability, with its own files in docs/features/<slug>/. Pass 1 brainstorms a thin request, grills you on the feature only, and writes brief.md (at most five Musts, out of scope, which existing components it touches). Pass 2 adds only the decisions the feature needs to docs/decisions.md; a recorded decision is changed only if you agree, and is marked superseded, never deleted. Pass 3 adds at most three epics and about twelve backlog items to the end of docs/epics.md and factory/backlog.md, with no scaffold job. If the project has no test command yet, the first item is a test harness that the rest depend on.
  6. Run it. /software-factory:factory run works through the new items and parks only what needs you; or use /software-factory:factory next one job at a time. Each spec reads the feature brief its epic links.
  7. One change needs no plan. 
    > /software-factory:factory add CSV export to the evidence list, tenant-scoped
    The spec-writer inspects your repo, records a baseline test run, and picks the track (quick or full). Open decisions trigger a short grill. Then build, review, triage and approval run as in The loop. You can also add - [ ] description lines to factory/backlog.md by hand; keep each to five acceptance criteria or fewer.
  8. Review, merge, learn. Handle needs-human cards with approve or rework. Run /software-factory:factory retro now and then, and approve the pitfalls it proposes for CLAUDE.md.
Existing code, existing problems. Reviews judge the change against its spec. Problems that predate it are triaged as defer and logged, not fixed silently. If your baseline tests are already failing, the spec records that, so the builder is not blamed for it.

Planning in detail (Workflow A, step 2)

If you have only a vision statement and an idea, begin with /factory plan. It runs a planner agent in three passes and stops for your approval after each one. Nothing is built until the plan is approved.

> /factory plan A tool that helps small SaaS teams get SOC 2 ready faster by
  collecting evidence automatically and tracking controls.
PassPlanner writesYou do
1 Clarifydocs/vision.md, docs/product-brief.md, docs/open-questions.mdIf your idea is only a sentence or two, you first brainstorm (the coach asks, you generate; options are narrowed with MoSCoW). Then you get grilled in rounds of numbered questions: product-defining ones ([open]) have no suggested answer so the call is yours; mechanical ones ([recommend]) do. You then answer any the planner adds. Progress is logged to docs/grill-log.md so an interrupted session resumes, and the result is a short docs/intent.md. Your answers are saved to docs/answers.md. Approve the vision and brief.
2 Architecturedocs/architecture.md, docs/decisions.md (one record per choice: stack, datastore, auth, hosting, tests, CI)Read the pre-mortem (the planner's list of how this product most likely fails, and which decision prevents each), then approve the stack or give notes. Notes go to docs/plan-notes.md and the pass re-runs.
3 Epics and backlogdocs/epics.md, a dependency-ordered factory/backlog.md, and docs/claude-md-proposal.mdApprove the order. On approval, the proposal is applied to CLAUDE.md (stack, test command, conventions).

The first backlog item is always the scaffold job: a project skeleton with a passing test, documented commands and CI. It is allowed to run before a test command exists, and it establishes one. After that, run /factory next repeatedly.

Every later spec, build and review also reads docs/vision.md, docs/architecture.md, docs/decisions.md and docs/epics.md, so small jobs stay consistent with the whole product and cannot silently contradict a recorded decision. When the last item of an epic merges, the factory runs a retro and reports which of the epic's "done when" checks hold.

Backlog lines look like - [ ] [E2] Evidence upload with audit trail; the [E2] tag links the job to its epic. You can resume an interrupted plan with /factory plan. Each pass allows up to three re-runs on your notes before the factory asks how to proceed.

One-time setup

  1. Fill in CLAUDE.md under Project context. At minimum, set the test command. Without it, the readiness gate stops every job at needs-human.
  2. Add only facts an agent cannot learn from the code: policy, frozen paths, non-default conventions. Skip directory trees and tech-stack lists.
  3. Make sure you have no uncommitted code changes and your default branch is checked out (init warns if not).
  4. Optional: start the dashboard. 
    python3 factory/server.py
# open the exact URL it prints (it ends in #t=..., a token that lets the page queue actions)
    For view-only you can still use cd factory && python3 -m http.server 8000.

The loop

1 Spec→ 2 Readiness gate→ 3 Build→ 4 Review (2–4)→ 5 Triage→ 6 Approve→ merged
StepWhoWhat happensOutput
1 Specspec-writer (Opus)Drafts intent, non-goals, numbered acceptance criteria (AC), assumptions, open decisions, baseline test run. Picks the track.spec.md
2 GateorchestratorNeeds intent, ACs and a test command. Open decisions mean a human must answer first.board update
3 Buildbuilder (Opus)Works on branch factory/<id>, writes tests per AC, commits, maps each AC to evidence.build.md + commits
4 Reviewsecurity (Opus); ux, ui, code (Sonnet)Run in parallel against the diff and the spec's intent. Round is complete only when every file exists.round-N/*.md
5 Triagetriager (Sonnet)Verifies each finding, sets severity, routes it (see below).round-N/triage.md
6 Decideorchestrator, then approver (Opus)The orchestrator first re-runs the tests on a clean copy of the branch (verify.md, branch.diff). On APPROVE the orchestrator merges into the default branch; the approver itself never merges. ESCALATE marks needs-human.decision.md

Quick vs full track

quickfull
WhenSmall, obvious, one areaTouches auth, data, several areas or UI flows
Reviewerssecurity + codesecurity + ux + ui + code

Sign-off criteria. An acceptance criterion tagged [sign-off] can only be met by a person, for example a product-owner OK or an on-device check. Tests or agents never count. The job builds and is reviewed as usual, then waits for you. Record it early with /factory signoff <id> while the job builds, or at the end with /factory approve <id>.

How triage routes findings

RouteMeaningEffect
dismissNoise, refuted or unsubstantiated (reason recorded)Ignored
patchOne clear fixBuilder fixes it next round
deferProblem existed before this change. Problems the change caused are never deferred.Logged, not fixed
decisionSeveral reasonable fixes or a product callJob goes to needs-human
Round cap. At most two review rounds. If patch items remain after round 2, the approver decides, and will usually escalate. A /factory rework grants two more rounds.

Worked example

A. Smooth run

> /factory add a GET /health endpoint that returns {"status":"ok"}
  1. Job 001-health-endpoint is created. The spec-writer reads CLAUDE.md, runs the baseline tests and writes: 
    # Health endpoint
Track: quick
## Intent        Let monitors check that the service is up.
## Non-goals     No dependency checks, no auth.
## Acceptance criteria
AC1: GET /health returns 200 and JSON {"status":"ok"}
AC2: Response needs no authentication
## Baseline      `npm test` - 42 passed
## Open decisions (none)
  2. The gate passes. The builder creates factory/001-health-endpoint, adds the route and two tests, commits, and writes build.md mapping AC1 and AC2 to test names.
  3. Quick track, so two reviewers run in parallel: 
    round-1/security.md  VERDICT: PASS
round-1/code.md      VERDICT: CHANGES   (code.md:  src/health.ts:12 - returns 200 even when shutting down? ...)
  4. The triager checks the code finding, finds it is outside the spec, and writes TRIAGE: CLEAN with that finding marked dismiss: out of scope, see Non-goals.
  5. The orchestrator re-runs the tests on a clean copy of the branch and writes verify.md (VERIFY: PASS). The approver sees evidence for both ACs and writes APPROVE. The orchestrator merges with git merge --no-ff and the card moves to done.

B. Needs a human

> /factory let users export audit evidence

The spec-writer lists under Open decisions: "Which formats (CSV, PDF)? Should exports be tenant-scoped?" The readiness gate sees open decisions and moves the job to needs-human before any code is written.

> /factory rework 002-export-evidence use CSV only, tenant-scoped, max 10k rows

Your note is appended to the spec/build files and the job continues. Answering questions early is cheaper than reviewing the wrong build.

C. Escalation after review

Round 1: security reports a missing authorization check (high). Triage verifies it, marks it patch. The builder is sent back (the same agent where possible, otherwise a fresh one that reads the branch and the triage file) and fixes it. Round 2: all pass. If instead round 2 still had a high-severity patch item, the approver would write ESCALATE with a specific question, and you would run:

> /factory approve 003-roles-page      # accept as is, after reading decision.md
> /factory rework 003-roles-page ...   # or send it back

The skills and agents live in the installed plugin, not in your project, so updating the plugin updates them. The dashboard, server.py and this guide are copies in factory/: after updating the plugin (/plugin, then restart Claude Code), run /software-factory:init again. On a set-up project it upgrades those copies, the backlog header and the factory section of CLAUDE.md after one confirmation, and never rewrites your jobs, backlog items or docs. Factory commands remind you in one line when the project and plugin versions differ.

The dashboard

Run the server shown in Setup and open the URL it prints. It refreshes every 3 seconds.

  • Columns follow the stages: spec, build, review, triage, decision, needs-human, done.
  • Each card shows the track and one chip per reviewer per round: PASS, CHANGES or grey while pending.
  • needs-human cards are outlined in amber. Those are the ones waiting on you.
  • Click a card to read its spec, build notes, reviews, triage and decision.
  • Above the board: the run banner (state, counts, why a run stopped, Resume), the backlog queue (done, active, ready, waiting, parked, blocked) and epic progress.

Acting from the dashboard

Parked jobs appear under Needs you with their question and options; the recommended option is highlighted. Pick options (or Use recommendations), add a note if you want, and submit. Approve asks to confirm. The click is queued only. Then run:

> /software-factory:factory apply

Apply re-validates each action against the current board, re-runs the tests before any merge, and carries out approve, rework, sign off or resume. Results appear under Recent actions. Without the token (or with http.server) the buttons copy the equivalent command instead. The server listens on 127.0.0.1 only and can queue just those four actions, each only for a job that is waiting on it.

Your role

  • Write good one-liners. State the outcome, not the implementation.
  • Answer open decisions when a job lands in needs-human. Read decision.md before approving.
  • Approve changes to CLAUDE.md that the retro proposes. The factory never edits your project context on its own.
  • Own security calls. Anything touching auth, tenant isolation or audit data is a good candidate for your own read even after APPROVE.

Tips

  • Queue work in backlog.md as - [ ] description lines and run /factory next repeatedly, or let /factory plan <capability> write the lines for a bigger capability. One short outcome per line.
  • Keep jobs small. A spec with more than five ACs is usually two jobs.
  • When an agent keeps making the same mistake, record it as an Observed pitfall in CLAUDE.md. Add rules only after you have seen the mistake, and keep a rule even if nothing has broken recently.
  • Completed job folders stay in factory/jobs/; retros and later builds learn from them.

Troubleshooting

SymptomLikely cause and fix
Commands start with “Project files are from … run /software-factory:init”The plugin was updated but this project was not. Run /software-factory:init; it upgrades the dashboard, server and this guide after one confirmation.
“This project was upgraded with plugin …; update yours”A teammate used a newer plugin. Update yours from /plugin and restart Claude Code.
A job sits in spec to decision with nothing runningIts session was interrupted. /factory rework <id> resume after interruption restarts it from its files.
Job stops at needs-human immediatelyTest command missing in CLAUDE.md, or the spec has open decisions. Check spec.md. A project with no tests can get one from a feature plan, which puts a test-harness job first.
/factory plan says to run document firstThe repo has code but no docs/architecture.md and docs/decisions.md. Run /factory document, then plan again.
/factory plan asks to finish another plan firstOne plan runs at a time. Run /factory plan with no text to finish it.
"Working tree must be clean"Commit or stash your changes, then rerun.
Dashboard says it cannot load board.jsonServe it: run python3 factory/server.py and open the URL it prints; opening the file directly will not work.
Dashboard buttons say “Copy command”Open the exact URL server.py printed, including #t=.... A restarted server prints a new token.
“Queued” but nothing happenedQueued is not applied: run /factory apply in your Claude session.
A review file is missingThe round is incomplete by design. The orchestrator waits, and re-runs an agent once if its file is malformed.
Parked as MERGE BLOCKEDThe job was approved and verified, but your session's permission settings refused the merge, and the factory never works around a refusal. Click Merge the approved branch on the dashboard and run /factory apply, or run /factory approve <id>: your request is what lets the merge run. To stop it happening again, allow the factory's merges in this project: re-run /software-factory:init and say yes to the merge permission, or add Bash(git merge --no-ff factory/*) with /permissions.
Merge failsAnother job changed the same files. The dashboard flags this on the parked job (Conflicts with the default branch). Approving still works: it records your decision and sends the job back to merge the default branch in and be reviewed again. By hand: /factory rework <id> merge the default branch into the branch and keep both sides.
