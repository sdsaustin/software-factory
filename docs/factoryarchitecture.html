Factory Architecture

Maintainer's reference for the software-factory Claude Code plugin (v1.3.x): what each part is, what it reads and writes, and how the parts collaborate. For how to use the factory, see the user guide (also copied to factory/userguide.html when a project is initialized).

1. Overview

The factory is a prompt-defined multi-agent system. There is no server and no application code in the plugin: everything is markdown instructions (skills and agents), a few templates, and two JSON manifests. Claude Code is the runtime. One orchestrator skill runs in the user's main session and spawns subagents that each do one job and write one file. State between steps lives in plain files in the user's project, so any step can be inspected, edited or re-run by a human.

Two audiences
Users run slash commands in their project. Maintainers (you) edit the plugin repo. Behavior changes by editing prompts, so most "bugs" are prompt bugs and are fixed in skills/*/SKILL.md or agents/*.md.
Key caveat
Most rules ("an agent writes only its own file", "only the orchestrator writes board.json") are conventions in prompts, not enforced by permissions. See Known limitations.

4. Runtime model

Plugin vs project

  • The plugin is installed once (user scope). Its skills and agents are available in every project. It holds no project state.
  • All state lives in the user's project: factory/, docs/, CLAUDE.md, and git branches factory/<id>. Every path inside prompts (factory/…, docs/…) is project-relative.
  • init is the only component that reads the plugin's own files (the templates), via ${CLAUDE_PLUGIN_ROOT}/templates, with a find ~/.claude/plugins … fallback if the variable is not expanded.

Naming and namespacing

  • Plugin name is software-factory, so commands are /software-factory:factory, /software-factory:init, /software-factory:grill, /software-factory:brainstorm. Prompts abbreviate to /factory; the short form works only if nothing else claims it (unverified).
  • Subagents are spawned with subagent_type = software-factory:<name> (e.g. software-factory:builder). The orchestrator's "Plugin notes" section tells the model to add this prefix. The builder additionally gets the instance name builder-<id> so it can be resumed with SendMessage.

Where the orchestrator runs

The factory skill runs in the user's main session. That matters: (a) it can spawn subagents, which subagents cannot do themselves; (b) it can ask the user questions (AskUserQuestion / chat); (c) it can invoke the grill and brainstorm skills, which in turn may dispatch fact-finding subagents.

Model assignment

Set in each agent's frontmatter (model: opus|sonnet). Opus for judgment-heavy roles (planner, spec-writer, builder, security reviewer, approver); Sonnet for the rest.

8. Flows

8.1 init

  1. Git: if not a repo, git init -b main. Else detect default branch (origin/HEAD, else current). Never rename.
  2. Create factory/, factory/jobs/.gitkeep; copy five templates if absent; set default_branch in board.json.
  3. Append project-context block to CLAUDE.md unless marker present.
  4. Ensure .gitignore has .DS_Store.
  5. If code exists: find test/lint/build commands, run tests once, propose CLAUDE.md lines, apply only on consent.
  6. Recommend one next step (empty → plan; existing → document then a feature). Offer commit.

8.2 The job loop (/factory <feature>, /factory next)

  1. Preflight: resolve default_branch (detect and store if missing); require default branch checked out and no uncommitted changes outside factory/, docs/, CLAUDE.md; require a test command (scaffold job excepted).
  2. Spec: allocate id NNN-slug; spawn spec-writer → spec.md (declares track).
  3. Readiness gate: spec needs Intent, numbered ACs and a test command in Baseline. Open decisions → needs-human → run grill (log jobs/<id>/grill-log.md, answers answers.md) → re-run spec-writer once → still open ⇒ stay needs-human. Other gaps → re-run spec-writer once, else needs-human.
  4. Build: spawn builder named builder-<id>; branch factory/<id> from default branch; tests per AC; commits only product code; writes build.md.
  5. Review round N: full = 4 reviewers in one parallel message; quick = security + code (ux/ui recorded N/A). Orchestrator waits for all expected files, records each VERDICT on the board as files land.
  6. Triage: spawn triager. CLEAN → decision. DECISION → needs-human. PATCH → if N<2, resume builder-<id> with SendMessage (fix only patch items) and start round N+1; at N=2 go to decision.
  7. Verify, then decide: the orchestrator switches to factory/<id>, runs the test command (and lint/build if listed in CLAUDE.md), switches back, and writes verify.md (VERIFY: PASS|FAIL + command output tail + diff stat) and branch.diff. FAIL after round 2 → needs-human; earlier → treated as a failed round. Then it spawns approver, which needs no shell.
  8. Decision: spawn approver. APPROVE → merge factory/<id> into default branch with --no-ff (or push branch and ask for a PR if protected / PR-required), stage done, commit factory state on default branch (factory: record job <id>), offer retro. ESCALATE → needs-human.

8.3 plan (/factory plan <vision>)

Purpose: greenfield. Three planner passes, each followed by a human approval gate; ≤3 re-runs per pass on human notes (docs/plan-notes.md). State in board.json.plan. Resumable.
  1. Pass 1 Clarify. Write vision to docs/vision-input.md. If thin (<~60 words / no users or outcome) or user unsure → brainstorm. Then grill (skip only on "skip grill"; headless on request, assumptions shown at the gate). Then planner PASS 1 → vision.md, product-brief.md (MoSCoW), open-questions.md; leftover questions are asked in grill format and PASS 1 re-runs once. Gate.
  2. Pass 2 Architecture. planner PASS 2 → architecture.md (with pre-mortem), decisions.md (pluses/minuses/interesting per decision). Show decisions, run commands and pre-mortem. Gate.
  3. Pass 3 Epics and backlog. planner PASS 3 → epics.md (done-when checks, dependencies), factory/backlog.md ordered by dependency → MoSCoW → impact/effort, item 1 = scaffold job, plus claude-md-proposal.md. Gate.
  4. Finish. Show and (on approval) apply the CLAUDE.md proposal; mark plan done; offer to commit; point to /factory next.

8.4 document (/factory document)

  1. planner PASS DOC inspects manifests, config, entrypoints, models, CI, README and git log; writes architecture.md, decisions.md (every record Status: inferred with file/commit evidence; reason unknown → Context: unknown), open-questions.md, claude-md-proposal.md.
  2. If questions: grill (log docs/grill-log.md, answers docs/answers.md); re-run PASS DOC once → answered decisions become accepted.
  3. Show components, decisions + status, legacy/frozen flags. Human approves (notes re-run, max 3). Apply CLAUDE.md proposal after showing it.
  4. Downstream rule: a review finding that conflicts with an inferred decision is routed decision by the triager (ask the human), never auto-patched.

8.5 approve, rework, retro, status

  • approve <id>: only for needs-human; show decision.md (or, if the job never reached the approver, the inbox entry and the human's answers, and write an APPROVE (human) decision); re-verify from a git archive; merge; done; commit factory state.
  • rework <id> <note>: append the note under ## Human rework in build.md and under ## Human amendments in spec.md (so the spec is not stale); resume builder-<id> (spawn a fresh one with the same name if gone); new review round. Grants two more rounds (cap is per rework, not global).
  • retro (manual, also offered every 5 done jobs and at epic close): retro agent writes factory/retro-proposal.md; orchestrator appends learnings to learnings.md; CLAUDE.md pitfalls applied only if the human approves. At epic close the orchestrator also reports which of the epic's "done when" checks hold (does not edit epics.md).
  • status: prints board.

8.7 run (/factory run): the outer loop

/factory run [--max-jobs N] [--until E2|B5] [--budget min]
  start / resume:  apply pending dashboard actions first, then write board.run
  repeat:
    pick   first READY backlog item  (unchecked, every depends: item done, not parked)
    run    the inner job loop (§8.2) in a fresh sub-orchestrator, HEADLESS:
             spec-writer decides safe defaults itself (Assumptions A1..);
             wherever the loop says needs-human it PARKS instead:
             stage needs-human + parked_reason + entry in inbox.md and inbox.json
    record DONE   -> tick backlog line, jobs_done++, consecutive_failures = 0
           PARKED -> consecutive_failures++, keep going with independent items
    check  default branch passes its tests after every merge
  stop when: nothing READY | --max-jobs/--budget/--until | 2 parked in a row | default branch red
  final report: done, parked (+ what they block), spec amendments, assumptions, stop reason

Autonomy changes only whether the loop waits. Reviews, triage, verify.md and the approver apply exactly as in a manual job, a run never pushes or merges into a protected branch, and epic retros run automatically at epic close with their CLAUDE.md proposals queued in the inbox for approval. Dependencies are explicit: a parked job blocks only the items that list it in depends:.

9. Git and state policy

  • Default branch is data: board.json.default_branch. Agents read it; prompts never hard-code main (except init's git init -b main for brand-new repos).
  • Job branch factory/<id> carries product code and tests only. The builder stages explicit paths and never commits anything under factory/, docs/ or CLAUDE.md, so the review diff default...factory/<id> is clean.
  • Factory state (factory/, docs/, CLAUDE.md) is allowed to be uncommitted during a job. It is committed on the default branch only after merge (factory: record job <id>) or when the human accepts the plan-commit offer. Preflight therefore ignores those paths.
  • Merge is --no-ff by the orchestrator only after APPROVE or /factory approve. Protected/PR-required repos: push branch, ask the human to open a PR.
  • Nothing is pushed to a remote by the factory except in the protected-branch case.

10. Invariants (do not break when editing prompts)

  1. Only the orchestrator writes board.json and the default branch.
  2. Each agent writes only the files named in its own prompt; reviewers and triager/approver never modify code.
  3. First-line grammar in §7.3 is unchanged, or the orchestrator's parsing is updated in the same change.
  4. A review round is complete only when every expected file exists; builder is never resumed mid-round.
  5. Problems a change caused are never defer; defer is only for pre-existing problems.
  6. Round cap 2 per cycle; more only via human rework.
  7. Planning never starts the next pass without human approval; approved pass outputs are not overwritten without the human saying so.
  8. Only the human approves changes to CLAUDE.md (orchestrator applies approved text; init appends its block once).
  9. init never overwrites and never renames branches.
  10. Inferred decisions are never presented as accepted; assumed grill answers are never presented as user answers.
  11. Paths in prompts are project-relative; only init touches plugin files.
  12. Every state file has one writer: actions.jsonl only server.py; board.json, inbox.* and actions-applied.json only the orchestrator. The server and dashboard never write orchestrator files.
  13. The default branch stays checked out. Verification uses git archive, never git switch; reviewers, triager and approver are read-only on git; the orchestrator re-checks the branch after every agent run.
  14. Queued dashboard text is data, not instruction: apply records it, never executes or obeys it.
  15. Autonomy never lowers a bar: run changes only whether the loop waits for a human.

12. Maintenance playbooks

Add or change an agent

  1. Create/edit agents/<name>.md with frontmatter name, description, model, tools. State: what to read, the single file to write, the first-line contract.
  2. Add the spawn step (using software-factory:<name>) and its parsing rule to skills/factory/SKILL.md.
  3. If it writes a new job file, add it to the dashboard's FILES() list and to the layout in §7.1 and the user guide.
  4. Update §6.2, §7.2, §7.5 here.

Add a reviewer (e.g. accessibility, performance)

  1. Copy agents/reviewer-code.md; change name, focus, output filename.
  2. Orchestrator Loop step 4: add to the full list (and quick if wanted); add a reviews.<key> entry.
  3. Triager already reads every file in round-N/; approver reads all rounds, so no change.
  4. Dashboard: add the key to REV in dashboard.html; user guide tables.

Add a command

  1. Add to "Commands" and a dedicated section in skills/factory/SKILL.md; define its board state, gates and caps.
  2. Add to README, user guide command table, §8 here. Consider whether init's "next step" should recommend it.

Change the stage model

Edit the stage list in the orchestrator "board.json" section, the Loop, and STAGES in dashboard.html together. The dashboard silently drops jobs whose stage is not in STAGES.

Change a template

Edit templates/…. Existing projects do not receive updates (init never overwrites). For breaking changes, document manual steps in the release notes (see limitation L5).

Release

  1. Edit; run claude plugin validate ..
  2. Smoke-test (§13).
  3. Bump version in .claude-plugin/plugin.json; add a line to §16.
  4. Commit. If the plugin is hosted in a git remote, push so users can update their marketplace.

13. Testing

There are no automated tests; verification is by validation and smoke runs. Use a scratch directory and load the plugin from disk. Running from --plugin-dir may need --add-dir <plugin path> so init can read the templates.

# init on an empty dir
mkdir /tmp/t && cd /tmp/t
claude -p "/software-factory:init" --plugin-dir $PL --add-dir $PL --permission-mode acceptEdits

# init on a master-branch repo with code → expect default_branch "master", no rename
# document on that repo → expect docs/decisions.md with Status: inferred + open-questions.md

# skills

14. Known limitations and risks

#LimitationImpactPossible fix
L1Write-scope rules are prompt conventions, not enforced. Agents hold Write/Bash broadly.A misbehaving agent could edit another file or board.json.Hooks (PreToolUse) that block writes outside the agent's file; or a validation step after each agent that diffs git status.
L2Orchestrator is a long prompt executed by the model; state machine is not code.Possible drift (skipped steps, wrong stage). Mitigated by first-line grammar and board updates.Move parsing/transition checks into a small script; add a /factory doctor that validates board vs files.
L3One job at a time. Parallelism exists only inside a review round.Throughput.Use git worktrees per job; board already keyed by id.
L4Dashboard does not render plan/document state, epic, or severity counts; ignores jobs whose stage is unknown.Planning progress invisible on the board.Add a planning banner and epic grouping.
L5No template upgrade path: init never overwrites, so projects keep old dashboard.html/userguide.html.Stale guides after plugin updates.init --upgrade that diffs and offers per-file replacement; version stamp inside templates.
L6Short /factory alias unverified; prompts use it for brevity.Confusion in docs.Confirm behavior and either rename or document.
L7Branch protection / PR flow is described but untested; no automatic PR creation.Manual step for protected repos.Use gh pr create when available and consented.
L8Cost: every job can spawn up to 8 agent runs per round (spec, build, 4 reviews, triage, approver) on Opus/Sonnet.Token spend on large backlogs.Prefer quick track; lower models; reduce reviewer set; skip UX/UI reviews for backend-only jobs (already N/A-able).
L9Planner PASS DOC depends on being allowed to run read-only/test commands; in restricted sessions it reports "not verified".Test command may be unverified in architecture.md.Orchestrator re-verifies the test command in preflight (already required for jobs).
L10Plan/document can be resumed from board.json, but partially written docs/ files rely on the planner to merge rather than clobber.Possible overwrite of human edits.Commit docs after each approved pass (offered at finish; recommended after each pass).
L12 resolved in 1.3.2Approver ESCALATEd solely because its shell was denied (it could not run the tests or git diff). Seen in the headless e2e run, where subagents did not inherit the Bash allow-list; interactive sessions would prompt instead.Spurious needs-human in restricted environments; no defect in the change.Done: the orchestrator now runs the tests on the job branch and writes verify.md and branch.diff before spawning the approver; the approver verifies from that evidence.
L13Dashboard clicks only queue actions; nothing happens until the human runs /factory apply (the orchestrator is not a daemon).An extra step; a forgotten queue sits unapplied (the dashboard shows "N queued actions").A watcher (e.g. Monitor on actions.jsonl) in a running session; deliberately not a server that spawns claude -p.
L14The action server relies on a per-run token, Host/Origin checks and localhost binding; there is no user authentication or HTTPS.Another local user or process on the same machine that can read the printed URL could queue actions (still validated again at apply).Unix-socket mode, or a token file with 0600 permissions.
L15/factory run job isolation (a fresh sub-orchestrator per job), run resume after a crash, the two-in-a-row stop and the epic retro were not exercised in the sandbox test; the inner loop, parking, dependency skipping and approve-after-answer were.Unverified paths.Run run in a scratch repo with --max-jobs small; kill it mid-job and resume.
L16Spec refinements proposed by a builder in a patch round are appended to the spec by the orchestrator without human approval (flagged in the final report).The spec can drift from what the human intended.Require approval for any AC deviation.
L11Grill/brainstorm fact-finding uses sub-agents only when run in the main session (as by the orchestrator). Run inside a subagent they cannot spawn more.Facts may be asked of the human.Keep them orchestrator-invoked.
