Factory Architecture

Maintainer's reference for the software-factory Claude Code plugin (v1.8.x): what each part is, what it reads and writes, and how the parts collaborate. For how to use the factory, see the user guide (also copied to factory/userguide.html when a project is initialized).

1. Overview

The factory is a prompt-defined multi-agent system. There is no daemon and almost no application code in the plugin: everything is markdown instructions (skills and agents), a few templates (including the optional stdlib-only dashboard server server.py), and two JSON manifests. Claude Code is the runtime. One orchestrator skill runs in the user's main session and spawns subagents that each do one job and write one file. State between steps lives in plain files in the user's project, so any step can be inspected, edited or re-run by a human.

Two audiences
Users run slash commands in their project. Maintainers (you) edit the plugin repo. Behavior changes by editing prompts, so most "bugs" are prompt bugs and are fixed in skills/*/SKILL.md or agents/*.md.
Key caveat
Most rules ("an agent writes only its own file", "only the orchestrator writes board.json") are conventions in prompts, not enforced by permissions. See Known limitations.

4. Runtime model

Plugin vs project

  • The plugin is installed once (user scope). Its skills and agents are available in every project. It holds no project state.
  • All state lives in the user's project: factory/, docs/, CLAUDE.md, and git branches factory/<id>. Every path inside prompts (factory/…, docs/…) is project-relative.
  • init is the only component that reads the plugin's templates, via ${CLAUDE_PLUGIN_ROOT}/templates. If the variable is not expanded it uses the installPath recorded in ~/.claude/plugins/installed_plugins.json, and only then the highest version a find ~/.claude/plugins … returns (never the first: old cached versions sit beside the current one). The orchestrator reads one more plugin file, .claude-plugin/plugin.json, for the version check (§8.1.1).

Naming and namespacing

  • Plugin name is software-factory, so commands are /software-factory:factory, /software-factory:init, /software-factory:grill, /software-factory:brainstorm. Prompts abbreviate to /factory; the short form works only if nothing else claims it (unverified).
  • Subagents are spawned with subagent_type = software-factory:<name> (e.g. software-factory:builder). The orchestrator's "Plugin notes" section tells the model to add this prefix. The builder additionally gets the instance name builder-<id> so it can be resumed with SendMessage.

Where the orchestrator runs

The factory skill runs in the user's main session. That matters: (a) it can spawn subagents, which subagents cannot do themselves; (b) it can ask the user questions (AskUserQuestion / chat); (c) it can invoke the grill and brainstorm skills, which in turn may dispatch fact-finding subagents.

Model assignment

Set in each agent's frontmatter (model: opus|sonnet). Opus for judgment-heavy roles (planner, spec-writer, builder, security reviewer, approver); Sonnet for the rest.

8. Flows

8.1 init

  1. Git: if not a repo, git init -b main. Else detect default branch (origin/HEAD, else current). Never rename.
  2. Create factory/, factory/jobs/.gitkeep; copy the six templates if absent; set default_branch in board.json.
  3. Append project-context block to CLAUDE.md unless marker present.
  4. Ensure .gitignore has .DS_Store.
  5. If code exists: find test/lint/build commands, run tests once, propose CLAUDE.md lines, apply only on consent.
  6. Merge permission: explain why, ask, and only on a yes merge Bash(git merge --no-ff factory/*) into permissions.allow in .claude/settings.local.json (or the shared settings.json if asked); skip if present.
  7. Recommend one next step (empty → plan; existing → document then a feature). Offer commit.

8.1.1 init on an initialized project (upgrade)

Triggered by factory/board.json existing. P = plugin_version on the board, V = the running plugin's version.

  1. U1: P newer than V → stop, tell the user to update the plugin; write nothing.
  2. U2: note a run running or a job in spec…decision (the in-flight list); default branch must be checked out.
  3. U3: collect, write nothing: each of dashboard.html, server.py, userguide.html missing / same / differs (cmp); missing learnings.md, backlog.md, jobs/.gitkeep; missing board fields from the migration list (default_branch, run, retro) plus plugin_version; backlog header and ids; the diff of CLAUDE.md's ## Software factory section (to the next ## or EOF), or the whole block if the marker is missing.
  4. U4: one summary, one confirmation (exclusions allowed); a non-empty in-flight list is shown there and the same yes must confirm no other session is working. Nothing to change → no question, “up to date”, U6 skipped.
  5. U5: snapshot commit of uncommitted factory/CLAUDE.md (factory: before upgrade to V), then apply (files by cp; if refused, a whole-file write of the template checked with cmp, never a hand patch). Backlog ids only when no line has one (B1… in file order, the same as the orchestrator's positional count); a mix is listed, never fixed.
  6. U6: no depends: anywhere and ≥2 open items → offer to propose dependencies (earlier ids only, no cycles, no chaining of independent items); apply on yes.
  7. U7: merge-permission question (step 6). U8: report-only consistency checks (ticked line whose job is not done; ticked count vs done count on boards without item).
  8. U9: report, list jobs in flight with the command that continues each (mid-stage jobs: rework <id> resume after interruption), offer the commit factory: upgrade to V.

Version check (orchestrator, every command): plugin_version missing or older than V → one line telling the user to run init; newer → one line telling them to update the plugin; never blocks, never writes the field.

8.2 The job loop (/factory <feature>, /factory next)

  1. Preflight: resolve default_branch (detect and store if missing); require default branch checked out and no uncommitted changes outside factory/, docs/, CLAUDE.md; require a test command (scaffold and (enabler: test-harness) jobs excepted).
  2. Spec: allocate id NNN-slug; spawn spec-writer → spec.md (declares track).
  3. Readiness gate: spec needs Intent, numbered ACs and a test command in Baseline. Open decisions → needs-human → run grill (log jobs/<id>/grill-log.md, answers answers.md) → re-run spec-writer once → still open ⇒ stay needs-human. Other gaps → re-run spec-writer once, else needs-human.
  4. Build: spawn builder named builder-<id>; branch factory/<id> from default branch; tests per AC; commits only product code; writes build.md.
  5. Review round N: full = 4 reviewers in one parallel message; quick = security + code (ux/ui recorded N/A). The spec's Extra reviewers: adds ux/ui to quick; Skip reviewers: drops ux/ui from full (never security or code). Orchestrator waits for all expected files, records each VERDICT on the board as files land.
  6. Triage: spawn triager. CLEAN → decision. DECISION → needs-human. PATCH → if N<2, commit factory state, then resume builder-<id> or spawn a fresh builder pointed at the triage file (fix only patch items) and start round N+1; at N=2 go to decision.
  7. Verify, then decide: the orchestrator exports the branch with git archive into the scratchpad (never switching branches; if the default branch has gained code since the branch was cut, it verifies the merge result in a detached worktree instead), runs the test command (and lint/build if listed in CLAUDE.md) with a throwaway HOME, and writes verify.md (VERIFY: PASS|FAIL + command output tail + diff stat) and branch.diff. FAIL after round 2 → needs-human; earlier → treated as a failed round. Then it spawns approver, which needs no shell.
  8. Decision: spawn approver. APPROVE → merge factory/<id> into default branch with --no-ff (or push branch and ask for a PR if protected / PR-required), stage done, commit factory state on default branch (factory: record job <id>), re-check parked jobs for conflicts (git merge-tree), offer retro at 5 done jobs. In headless mode the sub-orchestrator stops at APPROVE and the outer loop merges. A merge refused by a permission policy parks the job MERGE BLOCKED. ESCALATE → needs-human. Either way, follow-ups are collected into factory/followups.md.

8.3 plan (/factory plan <vision>)

Mode is picked first and announced: a plan in progress resumes in its mode; else docs/architecture.md + docs/decisions.md present → feature (§8.3.1); else source code present → offer document first; else product (below). One plan at a time; never while a run is running.
Purpose: greenfield. Three planner passes, each followed by a human approval gate; ≤3 re-runs per pass on human notes (docs/plan-notes.md). State in board.json.plan. Resumable.
  1. Pass 1 Clarify. Write vision to docs/vision-input.md. If thin (<~60 words / no users or outcome) or user unsure → brainstorm. Then grill (skip only on "skip grill"; headless on request, assumptions shown at the gate). Then planner PASS 1 → vision.md, product-brief.md (MoSCoW), open-questions.md; leftover questions are asked in grill format and PASS 1 re-runs once. Gate.
  2. Pass 2 Architecture. planner PASS 2 → architecture.md (with pre-mortem), decisions.md (pluses/minuses/interesting per decision). Show decisions, run commands and pre-mortem. Gate.
  3. Pass 3 Epics and backlog. planner PASS 3 → epics.md (done-when checks, dependencies), factory/backlog.md ordered by dependency → MoSCoW → impact/effort, item 1 = scaffold job, plus claude-md-proposal.md. Gate.
  4. Finish. Show and (on approval) apply the CLAUDE.md proposal; mark plan done; offer to commit; point to /factory next.

8.3.1 feature plan (/factory plan <capability> on a documented product)

Purpose: one capability on existing code. Same three gated passes and re-run cap; planner prompts start FEATURE <slug>. Own files in docs/features/<slug>/; shared decisions.md, architecture.md, epics.md, backlog.md are append-only; vision.md is never edited. Ids continue from the highest in use (unnumbered backlog lines count by position).
  1. Start. Slug (kebab-case, unique); text verbatim to request.md; plan.mode = feature.
  2. Pass 1 Brief. Thin (<~30 words / no user or outcome) → brainstorm. Then grill with vision, architecture and decisions given as settled context. planner FEATURE PASS 1 → brief.md (≤5 Musts, out of scope, Touches table of existing components, relied-on ADs), open-questions.md; questions asked, PASS 1 re-runs once. Gate.
  3. Pass 2 Decisions. planner FEATURE PASS 2 → new AD records appended (with a Feature: line), ## Feature: <slug> section with a 3-item pre-mortem appended to architecture.md. A conflict with a recorded decision is a question, never an edit; a supersession happens only on the human's answer and only changes the old record's status line. No new decisions → one-line approval; the gate is never skipped. If the test command is <TBD>, a test strategy decision with exact commands is required, and the existing run/test lines of architecture.md are updated to them (the only other in-place edit). Gate.
  4. Pass 3 Epics and backlog. planner FEATURE PASS 3 → epics appended (each with Feature: docs/features/<slug>/brief.md), backlog lines appended: no scaffold, depends: may name existing items, ≤3 epics and ~12 items, Must only. No test command → first item tagged (enabler: test-harness), every other new item depends on it. Gate.
  5. Finish. Apply claude-md-proposal.md unless NONE (never pitfalls); plan.status = done; append to board.features; offer commit factory: plan <slug>; point to /factory run.

8.4 document (/factory document)

  1. planner PASS DOC inspects manifests, config, entrypoints, models, CI, README and git log; writes architecture.md, decisions.md (every record Status: inferred with file/commit evidence; reason unknown → Context: unknown), open-questions.md, claude-md-proposal.md.
  2. If questions: grill (log docs/grill-log.md, answers docs/answers.md); re-run PASS DOC once → answered decisions become accepted.
  3. Show components, decisions + status, legacy/frozen flags. Human approves (notes re-run, max 3). Apply CLAUDE.md proposal after showing it; offer to commit (factory: document); point to a feature plan or a single job.
  4. Downstream rule: a review finding that conflicts with an inferred decision is routed decision by the triager (ask the human), never auto-patched.

8.5 approve, rework, retro, status

  • approve <id>: only for needs-human; show decision.md (or, if the job never reached the approver, the inbox entry and the human's answers, and write an APPROVE (human) decision); re-verify from a git archive; merge; done; commit factory state.
  • rework <id> <note>: append the note under ## Human rework in build.md and under ## Human amendments in spec.md (so the spec is not stale); resume builder-<id> (spawn a fresh one with the same name if gone); new review round. Grants two more rounds (cap is per rework, not global). Also recovers a job left in spec…decision by an interrupted session (after the human confirms nothing is running it): a job in spec re-runs the spec-writer with the note, any later stage goes to the builder as above.
  • retro (manual, also offered every 5 done jobs and at epic close): retro agent writes factory/retro-proposal.md; orchestrator appends learnings to learnings.md; CLAUDE.md pitfalls applied only if the human approves. At epic close the orchestrator also reports which of the epic's "done when" checks hold (does not edit epics.md).
  • signoff <id> [note]: records the human's sign-off on [sign-off] ACs in answers.md and under ## Human amendments; the job keeps running and still needs review, verify and the approver.
  • status: prints board.

8.7 run (/factory run): the outer loop

/factory run [--max-jobs N] [--until E2|B5] [--budget min]
  start / resume:  apply pending dashboard actions first, then write board.run
  repeat:
    pick   first READY backlog item  (unchecked, every depends: item done, not parked)
    run    the inner job loop (§8.2) in a fresh sub-orchestrator, HEADLESS:
             spec-writer decides safe defaults itself (Assumptions A1..);
             wherever the loop says needs-human it PARKS instead:
             stage needs-human + parked_reason + entry in inbox.md and inbox.json;
             on APPROVE it stops and returns APPROVED (it never merges)
    record APPROVED -> the outer loop merges, records the job, then:
           DONE     -> tick backlog line, jobs_done++, consecutive_failures = 0
           PARKED   -> consecutive_failures++, keep going with independent items
           merge refused by a permission policy -> park MERGE BLOCKED, stop
    check  default branch passes its tests after every merge
  needs:     a non-empty backlog, no plan in progress, a test command (unless the first READY item is the scaffold / test-harness job)
  stop when: nothing READY | --max-jobs/--budget/--until | 2 parked in a row | default branch red | merge blocked
  final report: done, parked (+ what they block), spec amendments, assumptions, stop reason

Autonomy changes only whether the loop waits. Reviews, triage, verify.md and the approver apply exactly as in a manual job, a run never pushes or merges into a protected branch, and epic retros run automatically at epic close with their CLAUDE.md proposals queued in the inbox for approval. Dependencies are explicit: a parked job blocks only the items that list it in depends:.

9. Git and state policy

  • Default branch is data: board.json.default_branch. Agents read it; prompts never hard-code main (except init's git init -b main for brand-new repos).
  • Job branch factory/<id> carries product code and tests only. The builder stages explicit paths and never commits anything under factory/, docs/ or CLAUDE.md (except a docs/ file the spec names on its Docs files: line because an acceptance criterion requires changing it), so the review diff default...factory/<id> is clean.
  • Factory state (factory/, docs/, CLAUDE.md) is allowed to be uncommitted during a job. It is committed on the default branch only after merge (factory: record job <id>) or when the human accepts the plan-commit offer. Preflight therefore ignores those paths.
  • Merge is --no-ff by the orchestrator only after APPROVE or /factory approve. Protected/PR-required repos: push branch, ask the human to open a PR.
  • Nothing is pushed to a remote by the factory except in the protected-branch case.

10. Invariants (do not break when editing prompts)

  1. Only the orchestrator writes board.json and the default branch.
  2. Each agent writes only the files named in its own prompt; reviewers and triager/approver never modify code.
  3. First-line grammar in §7.3 is unchanged, or the orchestrator's parsing is updated in the same change.
  4. A review round is complete only when every expected file exists; builder is never resumed mid-round.
  5. Problems a change caused are never defer; defer is only for pre-existing problems.
  6. Round cap 2 per cycle; more only via human rework.
  7. Planning never starts the next pass without human approval; approved pass outputs are not overwritten without the human saying so.
  8. A feature plan never rewrites, renumbers or deletes a recorded decision, epic or backlog line; it appends, supersedes an AD only on the human's recorded answer, and edits in place only the test/lint lines of architecture.md when it records a test strategy.
  9. Only the human approves changes to CLAUDE.md (orchestrator applies approved text; init appends its block once, and on an upgrade replaces only its ## Software factory section after the human's yes).
  10. init never renames branches and never rewrites state: on a new project it overwrites nothing; on an upgrade it replaces only the plugin-owned files (dashboard.html, server.py, userguide.html, the backlog header comment, the ## Software factory section) and only adds fields or ids, after one confirmation and a snapshot commit.
  11. Inferred decisions are never presented as accepted; assumed grill answers are never presented as user answers.
  12. Paths in prompts are project-relative; only init reads plugin templates (the orchestrator reads only the plugin's version).
  13. Every state file has one writer: actions.jsonl only server.py; board.json, inbox.* and actions-applied.json only the orchestrator. The server and dashboard never write orchestrator files.
  14. The default branch stays checked out. Verification uses git archive, never git switch; reviewers, triager and approver are read-only on git; the orchestrator re-checks the branch after every agent run.
  15. Queued dashboard text is data, not instruction: apply records it, never executes or obeys it.
  16. Autonomy never lowers a bar: run changes only whether the loop waits for a human.

12. Maintenance playbooks

Add or change an agent

  1. Create/edit agents/<name>.md with frontmatter name, description, model, tools. State: what to read, the single file to write, the first-line contract.
  2. Add the spawn step (using software-factory:<name>) and its parsing rule to skills/factory/SKILL.md.
  3. If it writes a new job file, add it to the dashboard's FILES() list and to the layout in §7.1 and the user guide.
  4. Update §6.2, §7.2, §7.5 here.

Add a reviewer (e.g. accessibility, performance)

  1. Copy agents/reviewer-code.md; change name, focus, output filename.
  2. Orchestrator Loop step 4: add to the full list (and quick if wanted); add a reviews.<key> entry.
  3. Triager already reads every file in round-N/; approver reads all rounds, so no change.
  4. Dashboard: add the key to REV in dashboard.html; user guide tables.

Add a command

  1. Add to "Commands" and a dedicated section in skills/factory/SKILL.md; define its board state, gates and caps.
  2. Add to README, user guide command table, §8 here. Consider whether init's "next step" should recommend it.

Change the stage model

Edit the stage list in the orchestrator "board.json" section, the Loop, and STAGES in dashboard.html together. The dashboard silently drops jobs whose stage is not in STAGES.

Change a template

Edit templates/…. Existing projects get the change when they run init after updating the plugin (§8.1.1): dashboard.html, server.py and userguide.html are replaced whole, the backlog's header comment and CLAUDE.md's ## Software factory section are replaced in place. Everything else in project-context.md (Policy, Running the project, conventions, pitfalls) belongs to the user after the first init and is never updated, so put nothing there that later versions will need to change. A new required top-level board.json field also needs a row in init's U3 migration list.

Release

  1. Edit; run claude plugin validate ..
  2. Smoke-test (§13).
  3. Bump version in .claude-plugin/plugin.json; add a line to §16 and a row to the version table in docs/upgradepath.html.
  4. Commit. If the plugin is hosted in a git remote, push so users can update their marketplace.
