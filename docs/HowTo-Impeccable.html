Using Impeccable with the Software Factory

Impeccable is a design skill you install in the product repository. The factory still specs, builds, reviews and merges. You use Impeccable when a person needs to set the visual system, or to judge a screen, and you hand the factory the result as files and acceptance criteria. Command details live at impeccable.style. Factory usage lives in the user guide.

Impeccable is not a fifth factory skill. The plugin ships init, factory, brainstorm and grill. Leave Impeccable in the product repo. The factory will not call /impeccable for you.

1. How the two fit

The factory owns the loop

Vision, architecture, a backlog, then each job: spec, build on factory/<id>, security / UX / UI / code review, triage, approval, merge. Agents read CLAUDE.md, factory/learnings.md, and docs/vision.md, docs/architecture.md, docs/decisions.md and docs/epics.md when those exist. The builder implements the acceptance criteria. The UI reviewer reads the diff. Neither one opens a browser or restyles a page on its own.

Impeccable owns the craft session

One skill, a shared vocabulary (shape, polish, typeset, layout, and the rest), two durable files (PRODUCT.md, DESIGN.md), and a detector you can run with no model and no API key. Its live commands need you looking at a page. That is a session you run, then you bring the decision back to the factory.

Use Impeccable in two places:

  • Before a job, on the default branch, to decide who the screen is for and what it should look like. Commit that. The next spec and build read it.
  • After a job has built a screen, as a rework note, when you have looked at the result and want one named pass (polish, typeset, layout) without new product behaviour.

A /factory run stays headless. It will not sit in live mode, pick elements, or choose “bolder” versus “quieter” for you. Those change the product, and in this loop a change of taste is yours.

2. Install it in the product

Run this in the repository the factory builds, after /software-factory:init. Install into that project, with hooks off. Hooks that rewrite a file while a job is in flight fight the spec and can leave the tree dirty, which blocks the next factory command.

npx impeccable install --no-hooks

When the installer asks, choose this project (not every project on the machine) and the harness you will design in. The factory’s own commands run in Claude Code, so include Claude there. If you shape screens in Cursor and build with the factory in Claude Code, install for both harnesses in this same repo. They share one PRODUCT.md and one DESIGN.md.

Reload the coding tool, then confirm the skill is there:

/impeccable

Update later with npx impeccable update. Impeccable is a separate project (pbakaus/impeccable, Apache-2.0). This plugin does not pin or vendor it.

Not in this plugin repo. If you are developing software-factory itself, skip Impeccable here. Install it in the product you are factory-building.

3. Record the design, then commit it

Impeccable writes two files at the repository root. Commit both on the default branch before the next /software-factory:factory next or run. A job refuses to start when anything outside factory/, docs/ and CLAUDE.md is uncommitted.

CommandWhenFileWhat it holds
/impeccable initOnce, as soon as you can name the usersPRODUCT.mdAudience, purpose, constraints, voice. Facts about the product, separate from the palette.
/impeccable documentOnce there is UI in the tree (after the scaffold, or on an existing app)DESIGN.mdThe visual system already in the code: type, color, radius, components.

init asks only for gaps it cannot see in the repo. Answer those yourself. A headless guess here becomes the system every later screen follows.

Keep the files at the root, where Impeccable writes them. The factory treats docs/ as its own memory (vision.md, architecture.md, decisions.md, epics.md). A builder may commit under docs/ only when a spec lists the file on Docs files:. Root PRODUCT.md and DESIGN.md stay product files you own.

When the visual system itself should change, do that in an Impeccable session on the default branch, commit it, and then let jobs follow the new file. A single screen that must depart from DESIGN.md says so in its spec, as an acceptance criterion, so the reviewers judge the departure on purpose.

Point CLAUDE.md at the two files

Factory agents read CLAUDE.md on every job. They do not read PRODUCT.md or DESIGN.md unless you name them. Under Non-default conventions in the project-context block, add:

### Non-default conventions
- PRODUCT.md is who the product is for and what job a screen does. DESIGN.md is the visual system (type, color, radius, components).
- Match both. Do not introduce a second palette, type scale, radius or component style.
- Change PRODUCT.md or DESIGN.md only when the spec says to.

That block is yours. Init and later upgrades leave it in place. They refresh only the ## Software factory section.

4. Which command, and when

Every command is /impeccable <command> <target>. The target is a route, a screen or a folder, in Impeccable’s own words (“the pricing page”, src/app/settings). Pin a command you use often with /impeccable pin audit, which adds a /audit shortcut.

MomentCommandsHow it comes back to the factory
Before any UI jobinit, document, shape, extractCommit PRODUCT.md and DESIGN.md on the default branch. Put the screen’s decisions in the feature request so the spec’s acceptance criteria name them.
You are looking at a built page and want one correctionpolish, typeset, layout, distill, clarify, harden, onboard, adapt, optimize, auditA rework note that names the command, the screen, and “keep the acceptance criteria.” The builder does the edit on factory/<id>. Review runs again.
You are in a browser, steering pixelslive, generate, craft, bolder, quieter, colorize, animate, delight, overdriveFinish the session yourself, on the default branch, before the job exists. Commit the result or write the decision into the spec. These need a person. A run will not drive them.
You want a second opinion on hierarchy or copycritiqueRead it. Fold anything you accept into grill answers or into the spec. The factory’s UX reviewer still checks flows, errors, empty states and accessibility against the acceptance criteria. Impeccable’s critique does not replace that file.
One pass, then review. A human rework grants two more review rounds. Ask for one named command. A chain of bolder, then delight, then overdrive on the same job is a new design, and it belongs in a spec before anyone builds it.

5. Three walks

A new product with a UI

factory init→ factory plan→ impeccable init→ scaffold→ impeccable document→ UI jobs
  1. Set up the factory and approve the plan. /software-factory:init, then /software-factory:factory plan <vision>. In grill, settle who the user is and what each major surface is for: persuade, operate, read, or experience. Those answers belong in docs/intent.md and docs/vision.md. Impeccable will ask the same kind of question; answer it once, in the plan, and repeat the short form in PRODUCT.md.
  2. Install Impeccable and write PRODUCT.md. npx impeccable install --no-hooks, then /impeccable init. Commit PRODUCT.md and the CLAUDE.md lines from above on the default branch.
  3. Let the scaffold land. /software-factory:factory next or run builds the skeleton. There is nothing to document visually before that.
  4. Write DESIGN.md from the skeleton with /impeccable document. If the skeleton has no real visual system yet, run /impeccable shape on the first screen you care about, with you in the loop, and commit the system it produces. Later jobs match that file.
  5. Start each UI backlog item with the screen named. “Settings page for a household admin, match DESIGN.md, empty state when there are no members.” A UI flow is a full-track job, so the UI and UX reviewers run. A small layout change can stay on the quick track and add the UI reviewer (Extra reviewers: ui). Say “include the UI reviewer” in the request when you want to be sure.

A product that already has code

  1. /software-factory:init, then /software-factory:factory document. That records architecture and decisions. Approve it.
  2. npx impeccable install --no-hooks, then /impeccable document. Read DESIGN.md. Fix anything the extractor got wrong before you commit it. Add the CLAUDE.md lines.
  3. If PRODUCT.md does not exist, run /impeccable init and commit it too.
  4. /software-factory:factory plan <capability>. For a screen whose direction is still open, run /impeccable shape first and put the outcome in the plan request. Feature-mode grill treats docs/vision.md, docs/architecture.md and docs/decisions.md as settled, so a visual choice you have not written down will be re-asked or assumed.
  5. Build with /software-factory:factory run or next. Before you approve a UI job, run the detector on the changed files, or open the page.

A built screen needs a design pass

The job is on factory/<id>. You are on the default branch. The page you want to correct is on the job branch. Leave that branch to the builder. A hand edit there never gets a build.md entry, so the next review sees a diff nobody accounted for, and an uncommitted edit on the default branch blocks the next job.

Look at the page (the builder’s dev server, or a preview of the branch). Then send one note:

/software-factory:factory rework 014-settings Polish the settings page to match DESIGN.md.
Keep every acceptance criterion. Do not add product behaviour.
Run `npx impeccable detect` on the UI files this job changed and fix the findings.

Name the command you mean: polish, typeset, layout, distill, clarify, harden. The builder implements that note, commits on the job branch, and a new review round runs. You approve after that round, the way you would any other rework.

Use live mode when you want to steer the screen yourself. Do it before the job, or after this job has merged, on the default branch. Then the next job’s spec describes the result.

6. The detector

The detector is the part that fits the factory’s verify step: a command, an exit code, findings with locations. It scans HTML, CSS, JSX, TSX, Vue and Svelte for AI-generated UI tells, accessibility problems and design-quality issues. No model, no API key.

npx impeccable detect src/
npx impeccable detect --github src/     # annotations CI can read
npx impeccable detect --json src/       # one object per finding
npx impeccable detect --list-rules      # the catalog, no scan

Run it yourself on the files a UI job changed, and paste anything you want fixed into the rework note. That keeps old screens out of the gate.

You can also put it on the lint line in CLAUDE.md once the existing UI is clean. The factory runs that command when it verifies a job, so a non-zero exit stops the merge. A scan of the whole tree will fail every later job, including a backend fix, until the old findings are gone. Wait until npx impeccable detect src/ exits 0 on the default branch, then add it next to the linter you already have. Leave the test command as the test command.

Scope it to this product. The rules flag common agent tells (one font everywhere, purple-to-blue gradients, cards nested in cards, gray text on a colored ground, a rounded icon tile above every heading). A product whose DESIGN.md deliberately uses one of those will fail the rule. Record that choice in DESIGN.md and in the spec, and treat that finding as accepted when you rework.

7. Hold the factory to the design

Three levers, all of them already in the factory. You do not need a new agent.

LeverWhat you writeWhat happens
The request“This changes the settings screen. Include the UI reviewer. Match DESIGN.md.”A quick job adds the UI reviewer (Extra reviewers: ui). A job that touches a UI flow, auth, data or more than one area is full track, which runs the UI and UX reviewers unless the spec skips them.
An acceptance criterionIn the spec, or in a plan note that becomes one: “The settings page uses the type, color and radius in DESIGN.md. npx impeccable detect reports no findings on the files this job adds.”The builder has to meet it, and the UI reviewer judges the diff against it. Anything beyond that list goes in ## Beyond the spec and the reviewers see it.
A [sign-off] criterion“[sign-off] A person has looked at the settings page at desktop and mobile width and accepts it against DESIGN.md.”Tests cannot close it. In a run the job still builds and reviews, then parks for you. You sign off from the dashboard or with /software-factory:factory signoff <id>. Use this when craft is the bar and a detector is not enough.

The UI reviewer checks consistency with components and tokens, layout, spacing, responsive behaviour, theming and hierarchy, from the diff. The UX reviewer checks flow, copy, errors, empty and loading states, and accessibility against the spec. Point both at DESIGN.md through CLAUDE.md and the acceptance criteria. A critique you liked is a note in the spec, not a second review file.

8. While a factory run is going

  • Leave Impeccable hooks off. npx impeccable install --no-hooks is the setup this guide uses. If you turned hooks on for a live session, turn them off before /software-factory:factory run.
  • Commit or discard PRODUCT.md, DESIGN.md and any screen edits first. run and next stop on a dirty tree outside factory/, docs/ and CLAUDE.md.
  • Let the run finish a job before you start an Impeccable session on the same files. One writer at a time: the builder on factory/<id>, you on the default branch between jobs.
  • Parked UI jobs wait in factory/inbox.md. A design correction is a rework, from the dashboard or from the command in section 5. Approving merges what was built.

9. Troubleshooting

What you seeWhat to do
/impeccable is unknownYou are in a session that started before the install, or the skill was installed in a different repo or harness. From the product root, run npx impeccable install --no-hooks again, reload, and start a new session.
The next factory command says the working tree must be cleanImpeccable left PRODUCT.md, DESIGN.md or source edits uncommitted. Commit them on the default branch, or discard them, then rerun.
A job ships a second paletteThe CLAUDE.md lines are missing, or the spec never mentions DESIGN.md. Add both, then rework the job with “match DESIGN.md; keep the acceptance criteria.”
npx impeccable detect fails on code this job did not touchKeep the detector out of the lint command until the default branch is clean. Put the findings that are in this job’s files into a rework note. Record pre-existing ones as follow-ups, or fix them in their own job.
Hooks rewrote a file during a buildReinstall with npx impeccable install --no-hooks, or turn hooks off in the harness, and discard the stray edit if it is not on the job branch. See section 8.
You polished the default branch and the job branch still has the old screenThe job’s diff is factory/<id>. Rework that job. Leave the default-branch polish for after the merge, or accept it as the new DESIGN.md and tell the rework to match it.
Live mode cannot find a dev serverStart the app the way CLAUDE.md describes, then /impeccable live. Live mode is a session of yours. The factory does not start it.
Two harnesses disagree about the designBoth should read the committed PRODUCT.md and DESIGN.md. Reinstall with project scope in the product repo. Delete a second copy if one harness wrote its own.
