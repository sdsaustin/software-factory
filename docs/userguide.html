Software Factory User Guide

How to use the software-factory plugin: turn a vague idea into a shipped product, or add features to code you already have. Every step is a file you can open. Maintainers who want internals should read Factory Architecture.

1. What you are using

The factory is a set of skills and agents that run in a Claude Code session. You describe the outcome. The factory writes a spec, builds it on its own git branch, has independent reviewers check the diff, and either merges it or stops with a specific question. Nothing runs in the background: the only server is an optional local dashboard (factory/server.py). State lives in factory/, docs/ and CLAUDE.md inside your project.

You keep the judgment

Who the product is for, what is in scope, which stack to use, and whether a risky change should merge. Those stops are called needs-human.

The factory keeps the paperwork

Specs, tests, reviews, triage and the merge. Each agent reads files and writes one file, so a long session can be resumed from disk.

Work is sized to the job. A one-line bugfix uses the quick track (security and code review). A feature that touches auth, data or a user flow uses the full track (security, UX, UI and code). The spec can adjust either: a quick job with a visible surface can add the UX or UI reviewer (Extra reviewers:), and a full job with no screen can drop UI or UX (Skip reviewers:). Security and code review always run. A whole product starts with a plan, then a queue of small jobs.

2. Install once, then init each project

Install the plugin in Claude Code:

/plugin marketplace add <path-or-github-repo-of-this-plugin>
/plugin install software-factory@software-factory

For local development of this repo: claude --plugin-dir /path/to/software-factory.

In the project you want to build, run init once:

/software-factory:init

Init creates factory/ (board, backlog, learnings, a live dashboard and a shorter in-project guide) and appends a project-context block to CLAUDE.md. It never overwrites a file that already exists, and it never renames your git branch. Re-running it is safe.

If the folder is not a git repo yet, init creates one on main. If it already is a repo, init records whatever the default branch is called (main, master, develop, trunk) as default_branch in factory/board.json. Jobs branch from that branch and merge back into it.

Init then asks whether the factory may merge approved jobs in this project. Say yes, and it adds one permission rule, Bash(git merge --no-ff factory/*), to .claude/settings.local.json. Without it, Claude Code's permission check (auto mode in particular) can refuse a run's merge, and every approved job then waits for your click. The rule covers only factory job branches, and a merge still needs an approval and passing tests.

Updating the plugin

Update software-factory from /plugin, restart Claude Code, then run /software-factory:init in each project. On a project that is already set up, init is the upgrade: it shows one summary (the dashboard, server and guide files that changed, missing board fields, backlog ids, and the diff of the ## Software factory section of CLAUDE.md), asks once, commits a snapshot first, and records the new version as plugin_version in board.json. Your jobs, backlog items, docs and learnings are never rewritten. Until you do, every factory command starts with a one-line reminder; if a teammate upgraded the project with a newer plugin, the reminder tells you to update yours. Details, and how to continue jobs that were in flight, are in the upgrade path.

Before a job. Be on the default branch, and have no uncommitted changes outside factory/, docs/ and CLAUDE.md. Planning, documenting, status and retros do not need a clean tree.

Brainstorm or grill?

They are two halves of one step. Brainstorm widens: it turns a vague idea into many options and helps you choose. Grill narrows: it takes the direction you chose and settles every decision under it. When the idea is vague, run brainstorm and then grill. When you already have a direction, go straight to grill.

Both skills keep an append-only log. If a session is interrupted, running the same skill again picks up from the log (status: open) instead of starting over. Both end the same way: they show your own answers back to you first, and only then point out the links and tensions they see.

A grill question looks like this:

❓ Q1 [open] - Who is a household member: anyone with the link, or invited accounts only?

❓ Q2 [recommend] - Conflict handling: two people tick the same item at once.
➡️ Last write wins, with a visible "updated by" line.

Run grill with no topic and it uses the current conversation or the most recent factory artifact (docs/vision.md, or a job's spec.md).

Inside an unattended factory run, the factory never grills mid-job. A job that needs your decision is parked in the inbox instead, and the run moves on.

Unattended (headless) sessions. Ask for an unattended plan, or start either skill and say the run is headless. Brainstorm then generates the ideas itself and marks every one (assumed). Grill answers each [recommend] question with its own recommendation, marked (assumed). It records each [open] question it cannot settle from your files as OPEN: and never invents an answer. A grill with OPEN lines left ends partial, and those questions come to you before the plan is approved.

Three kinds of numbered entry. D<n> are your grill decisions (grill-log.md). AD<n> are the planner's architecture decisions (docs/decisions.md). A<n> are assumptions written in a brief or spec. The prefix keeps them from colliding.

5. Start with a vague idea and finish with a product

Use this when you have a direction and little else. Nothing is built until you have approved a vision, an architecture and a backlog. The first built thing is a skeleton with a passing test. Features land one job at a time on the default branch.

Init→ Brainstorm→ Grill→ Plan × 3→ Scaffold→ Feature jobs→ Retro

The walkthrough

Imagine the only sentence you have is: “I want an app my household can use to share a grocery list.” That is thin (short, and it does not say who succeeds or what “done” looks like), so planning starts by helping you invent the product before it designs one.

  1. Make an empty project and init it. 
    mkdir grocery && cd grocery
claude
> /software-factory:init
    You get a git repo, factory/board.json, an empty backlog, and a CLAUDE.md whose test command is still <TBD>. That is expected. The scaffold job will fill it in.
  2. Hand the factory the sentence. 
    > /software-factory:factory plan I want an app my household can use to share a grocery list.
    The vision is saved verbatim to docs/vision-input.md. Because it is thin, brainstorm runs first. The coach asks one question at a time and does not invent the product for you. You generate options (shared list, recurring staples, aisle order, meal plans, receipt scanning, a household chat). The session is logged in docs/brainstorm-log.md. When you are done diverging, you sort with MoSCoW: Must / Should / Could / Won't-this-time. The result is docs/intent.md. A good Must for this story is “people in one household see the same list and can check items off.” Meal plans and receipt scanning go to Won't-this-time.
  3. Answer the grill. Grill then stress-tests that direction in rounds of numbered questions. Product-defining questions are tagged [open] and come with no recommended answer, so the call stays yours. Mechanical questions are tagged [recommend] and include a suggestion. A first round for this product might ask who is in a household, whether accounts are required on day one, and what “the list is shared” means if two people edit at once. Answers are appended to docs/grill-log.md and folded into docs/intent.md. An interrupted session resumes from the log.
  4. Approve pass 1 (clarify). The planner writes docs/vision.md and docs/product-brief.md. If it still has questions, they arrive in the same numbered format; your answers go to docs/answers.md and pass 1 runs once more. You read the summary and approve it, or you write notes. Notes are saved to docs/plan-notes.md and that pass re-runs (up to three times, then the factory asks how to proceed). Resume a stopped plan with /software-factory:factory plan and no extra text.
  5. Approve pass 2 (architecture). You get docs/architecture.md and docs/decisions.md: one record per choice (stack, datastore, auth, hosting, tests, CI), plus a pre-mortem — the ways this product is most likely to fail, and which decision prevents each. For the grocery list that might be “two people overwrite each other” prevented by a single shared list with last-write-wins and a visible updated-at, or “nobody can sign in” prevented by a magic-link and one household id. Push back in plain language. A note re-runs the pass.
  6. Approve pass 3 (epics and backlog). You get docs/epics.md and a dependency-ordered factory/backlog.md. Backlog lines look like - [ ] [E2] Check an item off from a second device. The [E2] tag ties the job to an epic. Each line is one outcome of at most twenty words; the exact rules and edge cases go in the job's spec, not the line. The first item is always the scaffold: project skeleton, a passing test, documented commands and CI. Scope stays small on purpose: about seven Must capabilities, at most eight epics, and roughly twenty-five Must backlog items. Should and Could live under ## Later in epics.md, so they are remembered and not built yet. If the plan is larger than that, trim it before you approve. On approval, a proposed project-context block is applied to CLAUDE.md (stack, test command, conventions). The factory will not invent “observed pitfalls” at this stage, because nothing has been observed yet.
  7. Build the skeleton. 
    > /software-factory:factory next
    next takes the first ready backlog line (unchecked, with its depends: items done) and runs it as a job (id like 001-scaffold). The line is ticked [x] only when that job merges; until then, the job's stage on the board shows its progress. This job is allowed to start without a test command, because its acceptance criteria create one. After it merges, later jobs have a real baseline.
  8. Build the product one item at a time. Repeat /software-factory:factory next, or let /software-factory:factory run do the whole list. Each job follows the loop: spec, build on factory/<id>, review, triage, approval, merge into the default branch, then a commit that records factory state (factory: record job <id>). Keep the dashboard open. A card outlined in amber is waiting on you; see when it asks. Anything the plan did not include can be added as a new - [ ] line, or started immediately with /software-factory:factory <feature>.
  9. Close an epic, then look back. When the last item of an epic merges, the factory checks that epic’s “done when” lines in docs/epics.md and tells you which ones hold. Run /software-factory:factory retro when you want a pause (it is also offered every five finished jobs). It proposes lessons. You approve the ones that should be written into CLAUDE.md.
What “finished” means here. The default branch contains the scaffold and every merged Must item. docs/vision.md, docs/architecture.md, docs/decisions.md and docs/epics.md are the product’s memory: every later spec and review reads them, so a small job cannot quietly contradict a decision you already made.
Commit the plan. After you approve a pass, commit docs/ and factory/. The factory offers a commit at the end (factory: plan). Those files are what an interrupted session resumes from.

Where you actually decide

If you want an unattended plan, say so. Grill and brainstorm will answer what they can, mark those answers (assumed), and list every assumption at the approval gate. They will not invent answers to open product questions; those stay open until you reply.

6. Add features to a product that already exists

Use this when the repository already builds and you want the factory to extend it. You do not plan the whole product. You write down what the code already decided, once, and then plan each new capability on top of it.

Clean tree, default branch→ Init→ Document→ Plan a capability→ Run
  1. Prepare the repo. Commit or stash your own code changes. Check out the default branch. If that branch is protected or requires pull requests, the factory will push factory/<id> and ask you to open the PR. It will not force a local merge.
  2. Init inside the repo. 
    > /software-factory:init
    Factory files are added beside your code. The project-context block is appended to CLAUDE.md if it is not already there. Because source files exist, init looks up the test, lint and build commands, runs the tests once, and shows you the exact lines it wants to write. Approve them. Then add only facts an agent cannot learn by reading the code: a policy, a frozen or generated path, a convention that is not the framework default, a mistake you have actually seen. Skip directory trees and tech-stack lists. Accept init's offer to commit: a job will not start while init's .gitignore change is uncommitted.
  3. Document what is already true. 
    > /software-factory:factory document
    The planner reads manifests, config, entrypoints, data models, CI and git history. It drafts docs/architecture.md and docs/decisions.md. Every decision starts as Status: inferred and cites the file or commit it came from. Where the code cannot say why, you are grilled (why this database, which areas are legacy, which conventions are law). Answered decisions become Status: accepted. You approve the component list, the decisions, and the proposed CLAUDE.md facts before they are applied, and the factory offers to commit (factory: document). Inferred decisions still bind later specs, but a conflict with an inferred decision is a question for you, not an automatic failure. You do this once per repo.
  4. Plan a capability. 
    > /software-factory:factory plan let customers invite teammates and revoke access
    Because docs/architecture.md and docs/decisions.md exist, plan runs in feature mode and says so. It plans this one capability, not the product, in the same three approved passes. Everything it writes for itself goes in docs/features/<slug>/ (here team-invites), so the next capability's plan never collides with this one.
    • Pass 1, the brief. Brainstorm runs first if the request is thin. Grill then asks only about the feature: your vision, architecture and decisions are treated as settled. The planner writes brief.md: who it is for, the outcome, at most five Musts, what is out of scope, and which existing components it touches. You approve.
    • Pass 2, new decisions only. Every recorded decision stays binding. The planner appends only what this feature needs (numbering continues, for example AD14), adds a ## Feature: team-invites section with a short pre-mortem to architecture.md, and lists the existing decisions it relies on. If the feature needs a recorded decision changed, you are asked; the old record is marked superseded by AD<n> only if you agree, and nothing is deleted. If nothing new is needed, you approve with one line.
    • Pass 3, epics and backlog. New epics are added to docs/epics.md, each linking back to the brief, and new lines are added to the end of factory/backlog.md with ids that continue from yours. There is no scaffold job. Each line is one short outcome (at most twenty words). A feature plan stays small: at most three epics and about twelve items, all Must. Anything bigger is a second feature plan. If you give a note at this gate (for example "merge B12 and B13"), the pass re-runs and replaces its own lines; it never adds them twice.
    The factory offers a commit (factory: plan team-invites).
  5. Build it. 
    > /software-factory:factory run
    The run works through the new items and parks only the ones that need you; see Let it run on its own. Or go one job at a time with /software-factory:factory next. Each job's spec-writer reads the feature brief its epic links, so specs stay inside the feature's Musts and out of scope.
One change does not need a plan. For a change you can state in a sentence, skip the plan: /software-factory:factory add a CSV export of the evidence list, scoped to the current tenant. If something is a real product choice with no safe default (CSV or PDF, who may export), the job stops and grills you before any code is written. You can also add lines to factory/backlog.md by hand, for example - [ ] Filter the evidence list by control id, and run them with next or run.
No test suite yet? If CLAUDE.md still has no test command, the feature plan records a test strategy decision with the exact command, writes it into CLAUDE.md, and makes the first backlog item a test harness ((enabler: test-harness)) that every other new item depends on. That one job may start without a working test command because it creates one.
Pre-existing bugs stay pre-existing. Reviews judge the change against its spec. A problem that was already in the code is triaged as defer and logged. It is not fixed inside the feature job. If the baseline tests are already failing, the spec records that, so the builder is not blamed for it.

7. Ship one small change

Use this for a change whose behavior you can state in a sentence and whose blast radius is one area: a health check, a copy fix, a validation rule, a bug with an obvious correct result.

> /software-factory:factory add a GET /health endpoint that returns {"status":"ok"}

A smooth run looks like this:

  1. Job 001-health-endpoint is created. The spec-writer records Track: quick, two acceptance criteria (200 and that JSON body; no authentication), the baseline test command, and no open decisions.
  2. The builder creates branch factory/001-health-endpoint, adds the route and tests, commits, and writes build.md mapping each acceptance criterion to a test name. Factory state is not committed on that branch. The orchestrator then runs the tests once on a clean copy of the branch and writes verify.md and branch.diff; a failure goes back to the builder before any reviewer starts.
  3. Quick track runs two reviewers in parallel. Security passes. Code review might flag something the spec called a non-goal (for example, behavior during shutdown). Triage marks that finding dismiss and writes TRIAGE: CLEAN.
  4. The approver reads that evidence and writes APPROVE. The branch is merged with git merge --no-ff. The card moves to done.

Say the outcome, not the file to edit. “Return 200 and {"status":"ok"} from GET /health with no auth” gives the spec-writer acceptance criteria. “Add a function in src/health.ts” does not.

8. A big capability, split into jobs

Use this when the ask is a capability, not a change. “Add billing”, “let customers invite their team”, or “support SOC 2 evidence collection” will make a spec with too many acceptance criteria, and the review will thrash.

On a product that already exists, use a feature plan: /software-factory:factory plan <capability>. It settles the shape with brainstorm and grill, records the decisions later jobs must share, and writes the ordered backlog lines for you. See Plan a capability.

On a brand-new product you do not do this separately: pass 3 of the product plan already produces the ordered backlog.

By hand, if you prefer: grill the capability (/software-factory:grill let customers invite teammates and revoke access), add the decisions later jobs must share to docs/decisions.md, then write backlog lines small enough for about five acceptance criteria each, in dependency order, and run them with next or run:

- [ ] Invite a teammate by email to the current tenant
- [ ] Accept an invite and land in that tenant
- [ ] Remove a teammate and invalidate their session

Each one still gets its own spec, branch, review and merge. The second job sees the first job’s code on the default branch.

Follow-ups. Reviewers note out-of-scope problems under ## Follow-ups, and the factory collects them, once each, in factory/followups.md. Nothing there is built on its own. When two jobs have deferred the same issue, the factory marks it (proposed) and asks whether to add it to the backlog. You decide, and you can delete or promote any line yourself.

Let it run on its own, and answer once at the end

Instead of repeating next, run /software-factory:factory run after the plan is approved. It works through the whole backlog on its own, one job at a time, using the same loop and the same bars (reviews, triage, tests, approver). A job that needs you is parked, not waited on: its question goes to factory/inbox.md and inbox.json, and the run carries on with every item that does not depend on it. Items that do depend on a parked job simply wait.

  • Without a human in the loop the spec-writer decides every safe-default choice itself and records it under Assumptions (A1, A2, ...). The run report lists them so you can override any.
  • The backlog gives each item an id and its prerequisites: - [ ] B3 [E1] Report (depends: B2). The planner writes these.
  • Flags: --max-jobs N, --until E2 (or B5), --budget <minutes>.
The run stops whenWhy
No item is readyEverything is done, or what is left waits on a parked job
A limit you set is reached--max-jobs, --budget, --until
Two jobs in a row were parkedUsually one systemic problem (a bad decision, a flaky test command), not two bad jobs
The default branch fails its tests after a mergeEverything built next would sit on a broken base
A merge was refused by your permission settingsEvery later merge would be refused too. The job is parked as MERGE BLOCKED; approve it from the dashboard (or /factory approve <id>) and the factory merges it. To prevent it, say yes when /software-factory:init offers the merge permission (Bash(git merge --no-ff factory/*))

The background job for each item stops once the approver approves; the run itself, in your session, does the merge. A run never pushes and never merges into a protected default branch; those jobs are parked as NEEDS PR.

Answer from the dashboard

Each parked job appears in the dashboard’s Needs you panel with its question and the options, the recommended one highlighted. Pick an option (or use Use recommendations), add a note if you like, and submit. Approving asks for one more confirmation. The click is only queued; nothing runs until you tell the factory in your Claude session:

> /software-factory:factory apply

Apply re-checks every queued action against the current board, then carries it out: approve re-checks the test evidence before merging (re-running the tests from a clean copy of the branch if the code has moved), rework sends the job back with your answers and note, resume continues the stopped run. Results show under Recent actions on the dashboard. You can also skip the dashboard and use approve, rework and run resume directly.

Two common shapes:

A decision before any code

> /software-factory:factory let users export audit evidence

Open decisions: which formats, and whether an export may include another tenant’s rows. The job waits. You reply:

> /software-factory:factory rework 002-export-evidence CSV only, current tenant, at most 10k rows

That note is appended to spec.md under Human amendments (it overrides anything above it) and to build.md. Reviewers judge the amended intent. A human rework grants two more review rounds.

A review that found a real defect

Round 1: security reports a missing authorization check. Triage verifies it and marks it patch. The builder is sent back to fix it (the same agent where possible, otherwise a fresh one that reads the branch and the triage file). Round 2 passes, and the job can merge. If a high-severity patch is still open after round 2, the approver escalates. You then either accept it:

> /software-factory:factory approve 003-roles-page

or send a concrete note:

> /software-factory:factory rework 003-roles-page hide the page until the membership check passes

There are at most two review rounds per cycle. /software-factory:factory approve <id> is only for a job already in needs-human. The factory shows you decision.md before it merges.

10. What happens inside one job

1 Spec→ 2 Gate→ 3 Build→ 4 Review→ 5 Triage→ 6 Approve→ merged
StepWhoWhat you get
Specspec-writerfactory/jobs/<id>/spec.md — intent, non-goals, numbered acceptance criteria, assumptions, baseline test run, and Track: quick or full
GateorchestratorBuild starts only when intent, acceptance criteria and a test command are present. Open decisions stop the job first.
Buildbuilder, on factory/<id>Code, tests, and build.md mapping each acceptance criterion to evidence
Verifyorchestratorverify.md and branch.diff: the tests run once on a clean copy of the branch. A failure goes back to the builder for one fix before any reviewer starts; reviewers and the approver read this result instead of re-running the suite.
Reviewreviewers, in parallelround-N/security.md and code.md; full track also writes ux.md and ui.md. A round is complete only when every expected file exists.
Triagetriagerround-N/triage.md. CLEAN goes to approval. PATCH sends the builder back if this is round 1. DECISION asks you. When every reviewer passes with no findings, the orchestrator writes CLEAN itself and the triager does not run.
Decideapprover, on fresh test evidence (re-run only if the code moved)decision.md. APPROVE merges. ESCALATE waits for you. The approver does not merge; the orchestrator does, after approval.

How findings are routed

RouteMeaningWhat happens
dismissNoise, or already outside the spec (the reason is recorded)Ignored
patchOne clear fixThe builder fixes it on the next round
deferThe problem existed before this changeLogged, not fixed in this job
decisionMore than one reasonable fix, or a product callThe job becomes needs-human

Quick track is for a small, obvious change in one area. Full track is for auth, data, several areas, or a UI flow. Security hardening of untrusted input is written as an acceptance criterion, so it is tested rather than left as a suggestion.

13. Watch the board

python3 factory/server.py
# open the exact URL it prints, e.g. http://127.0.0.1:8000/dashboard.html#t=...

The part after #t= is a token created each time the server starts; the page keeps it for that tab and uses it to queue actions. The server listens on 127.0.0.1 only. If the page is opened without the token, or served with python3 -m http.server, it is read-only and its buttons copy the equivalent command instead.

The page polls board.json every few seconds. Columns are the stages: spec, build, review, triage, decision, needs-human, done. Each card shows the track and a chip per reviewer (PASS, CHANGES, or pending). Amber means the job is waiting on you. Open a card to read the spec, build notes, reviews, triage and decision. Opening dashboard.html as a file will not load the board; it has to be served.

Above the board you also get: a run banner (state, done/in flight/parked counts, why it stopped, a Resume button), Needs you (parked jobs with clickable options, see Answer from the dashboard), the backlog queue (done, active, ready, waiting, parked, blocked) and epic progress.

What a click can and cannot do: it can queue exactly four things. It can approve a parked job, rework it with your note, sign off a job's [sign-off] criteria while it builds, or resume a stopped run, and only for a job that is actually waiting on that action. It cannot write board.json, merge, or run anything by itself. The server refuses other hosts and origins and any request without the token, and apply validates again before acting.

14. What to keep doing yourself

  • Write the outcome. Who can do what, and how you will know it works. Leave the file layout to the spec and the builder.
  • Check the assumptions after an unattended plan. Answers marked (assumed) in grill-log.md and answers.md were the factory's own recommendation, not yours. Change any you disagree with before the jobs run.
  • Stay available at the gates. Planning has three approvals. Jobs stop when a choice is actually yours. Answering before code is written is cheaper than reviewing the wrong build.
  • Read decision.md before /software-factory:factory approve <id>. Approval is a merge.
  • Read security-sensitive diffs yourself when a job touches auth, tenant isolation or an audit trail, including after APPROVE.
  • Put repeated mistakes into CLAUDE.md as observed pitfalls, after you have seen them. The retro drafts these; you approve them. The factory does not edit that section on its own.
  • Leave finished job folders in place. Later builds, reviews and retros read them.

15. Troubleshooting

What you seeWhat to do
Every factory command starts with “Project files are from … run /software-factory:init to upgrade them”The plugin was updated but this project was not. Run /software-factory:init and confirm the summary. See Updating the plugin.
“This project was upgraded with plugin …; update yours”, or init stops saying the project is newerA teammate upgraded the project with a newer plugin than yours. Update from /plugin, restart Claude Code, and carry on; do not downgrade the project files.
A job is stuck in spec, build, review, triage or decision and no session is running itThe session that ran it was interrupted. Run /software-factory:factory rework <id> resume after interruption; it restarts the job from its files.
The job stops at needs-human immediatelyOpen spec.md. Either the test command in CLAUDE.md is still <TBD>, or Open decisions is not empty. Answer, then let the spec run again.
A message that the working tree must be clean, or that the default branch is not checked outCommit or stash changes outside factory/, docs/ and CLAUDE.md, switch to the default branch, and rerun. /software-factory:factory status shows the branch name the factory recorded.
The dashboard cannot load board.jsonRun python3 factory/server.py and open the URL it prints (or python3 -m http.server inside factory/ for view-only).
Dashboard buttons say “Copy command” instead of queuingThe page has no token: open the exact URL server.py printed, including #t=.... After a server restart the old token is invalid; open the new URL.
A click shows “Queued” but nothing happensQueued is not applied. Run /software-factory:factory apply in your Claude session.
“Not queued: job is not waiting for a human”The board moved on after the page loaded. Wait for the next refresh.
A review file never appearsThe round waits until every expected reviewer has written a file. A malformed first line is re-run once.
The merge fails with a conflictAnother job changed the same files first. The dashboard flags it on the parked job. Approving still works: your decision is recorded and the job goes back to merge the default branch in and be reviewed again. To do it by hand: /software-factory:factory rework <id> merge the default branch into the branch and keep both sides.
Parked as MERGE BLOCKEDYour permission settings refused the merge. Run /software-factory:factory approve <id>, or click Merge the approved branch and run apply. To prevent it, re-run /software-factory:init and allow Bash(git merge --no-ff factory/*), or add that rule with /permissions.
A brainstorm or grill seems to start overIt resumes only from a log whose frontmatter says status: open. Check docs/brainstorm-log.md or docs/grill-log.md (for a feature plan, the ones in docs/features/<slug>/). A log marked complete starts a new session.
Backlog lines read like acceptance criteria (exit codes, formats, long lists)Give a note at the pass 3 gate, for example "one short outcome per line", and the pass re-runs. Details belong in the job's spec.
plan says to run document firstThe repo has code but no docs/architecture.md and docs/decisions.md. A feature plan builds on them. Run /software-factory:factory document, then plan again.
plan asks to finish another plan firstOnly one plan runs at a time. Run /software-factory:factory plan with no text to finish the one in progress, then plan the next capability.
The plan seems to restartRun /software-factory:factory plan with no new vision. Approved pass outputs are kept. A pass re-runs only when you give notes or explicitly ask.
