Upgrade path

Moving a project that is already part-built from an older software-factory plugin (for example 1.3.x) to 1.5.0, and carrying on where you left off. Worked example: 54 backlog items, 5 built.

Why an upgrade does not break a project in progress

All state lives in your project, not in the plugin: factory/board.json, backlog.md, learnings.md, factory/jobs/<id>/…, docs/…, and the job branches in git. The plugin supplies only the instructions (skills and agents). Every field added since 1.3.6 is optional, so an old board.json is valid as it stands and needs no migration. Old backlog lines such as - [ ] [E1] text keep working: they get positional ids and no dependencies.

1. Pre-flight (before touching anything)

  1. Let any running agent finish, or stop it.
  2. Commit or stash everything outside factory/, docs/ and CLAUDE.md, and check out your default branch. Builders often leave the job branch checked out, and the preflight refuses to start otherwise.
  3. Back up the state: 
    cp -r factory factory.bak
  4. Confirm nothing is half-done. Every job in factory/board.json should be done or needs-human. Anything in spec, build, review, triage or decision was caught mid-flight; see Resuming by state.
  5. Check that the done jobs and the ticked backlog lines agree. The old next ticked a line when a job started, so a [x] line whose job is not done is a stuck job. Fix it before going on.

2. Upgrade the plugin

  1. Open /plugin, go to Installed, and update software-factory. If no newer version is offered, refresh the marketplace first (/plugin marketplace update software-factory). Go by what the menu shows; these exact update commands were not tested for this document.
  2. Restart Claude Code. Skills load when a session starts.
  3. Confirm the version: 
    grep -A3 software-factory ~/.claude/plugins/installed_plugins.json
    The installPath should end in 1.5.0 (it ended in 1.3.6 before).

3. Refresh the project files

/software-factory:init never overwrites existing files, so your project keeps the old dashboard until you copy the new files over. Find the plugin folder with find ~/.claude/plugins -type d -path '*software-factory*/templates/factory', then:

cp <plugin>/templates/factory/dashboard.html  factory/
cp <plugin>/templates/factory/server.py       factory/
cp <plugin>/templates/factory/userguide.html  factory/
FileAction
dashboard.html, server.py, userguide.htmlCopy from the plugin
board.json, backlog.md, learnings.md, jobs/Leave alone. These are your state.
inbox.md, inbox.json, actions.jsonl, actions-applied.jsonDo not create. The orchestrator and the server create them when needed.

4. Add dependencies to the backlog (the step that matters for a long backlog)

Your backlog lines have no ids and no prerequisites, so /factory run treats every item as independent. If item 12 is parked for a human and item 13 really needs it, the run would still build 13 on a base that does not exist. Annotate the backlog first.

Do not re-run the planner for this. Planner Pass 3 regenerates the backlog. Ask Claude in an ordinary session to edit backlog.md in place.
Edit factory/backlog.md only. Give each line an id B1..B54 in order (keep the lines that are
already [x] exactly as they are). Add "(depends: B..)" only where an item truly cannot be built
or tested without another; use docs/epics.md and docs/architecture.md to decide. Do not change
any wording or any checkbox. Then list the dependencies you added so I can review them.

Read the result before accepting it:

  • Too few links is risky: a parked job will not stop items that need it.
  • Too many links is wasteful: one parked job then blocks everything after it. Independent items should not be chained.
  • Dependencies must point to earlier ids and must not form a cycle.

If you skip this step, use /software-factory:factory next one job at a time instead of run.

5. First run with the new features

  1. Start the dashboard. Stop any old python3 -m http.server first, then: 
    python3 factory/server.py
    Open the exact URL it prints, including the #t=… part; that token is what lets the page queue actions. It listens on 127.0.0.1 only and tries ports 8000 to 8020.
  2. Start small. Do not begin with all remaining items: 
    /software-factory:factory run --max-jobs 3
    Each job can spawn up to eight agent runs per round, so a full run is large. Watch the dashboard: the banner shows the run state, and parked jobs appear under Needs you.
  3. Answer parked jobs. Pick an option (the recommended one is highlighted) and submit. A click only queues the action. Then, in your Claude session: 
    /software-factory:factory apply
    Apply re-checks each action against the board, re-runs the tests from a clean copy of the branch before any merge, and records the result under Recent actions.
  4. Continue with /software-factory:factory run resume, or with a larger --max-jobs.
FlagUse it to
--max-jobs NCap how many jobs one run starts
--until E2 or --until B20Stop at an epic or item boundary
--budget <minutes>Cap wall-clock time

The run stops by itself when nothing is ready, when a limit is reached, when two jobs in a row are parked (usually one systemic problem), or when the default branch fails its tests after a merge.

Resuming by state

Where it stoppedHow to resume
Planning (plan.status in board.json)/software-factory:factory plan with no vision. It continues from the board and keeps approved passes.
A job in needs-human/software-factory:factory approve <id> or rework <id> <note>, or click it on the dashboard and run apply.
Between jobs (nothing in flight)/software-factory:factory next, or run to drain the rest.
A run that was stopped or crashed/software-factory:factory run resume (state is read from board.json run and the backlog).
Mid-job (stage spec, build, review, triage or decision)No automatic resume. See below.

Recovering a job caught mid-stage (manual)

Look in factory/jobs/<id>/ to see how far it got:

  • Only spec.md: the build had not started.
  • build.md present: the code is committed on factory/<id>.
  • A round-N/ folder with fewer review files than expected: the round was incomplete.

The simplest safe route: set the job's stage to needs-human in board.json (while no session is running), commit that, then run /software-factory:factory rework <id> <note>. That sends the job back to the builder with a fresh review round. Every subagent run starts clean from files, so redoing a step loses nothing.

Rollback

  1. Stop server.py and any session.
  2. Restore the state: rm -rf factory && mv factory.bak factory.
  3. Reinstall the older plugin version if you need the old behavior, then restart Claude Code.
  4. Job branches and merges already made are ordinary git history; revert them with git if needed.

Known gaps and risks

The upgrade itself, and recovery from a crash mid-run, were not tested on a real in-flight project. The loop, parking, dependency skipping, approve-after-answer and the dashboard actions were exercised in a sandbox. Start with --max-jobs 3 and compare against your expectations.
  • Run isolation (a fresh sub-orchestrator per job), the stop after two parked jobs in a row, and the per-epic retro are not yet exercised (limitation L15 in the architecture document).
  • Dashboard clicks only queue actions; nothing happens until you run /factory apply (L13).
  • Edit board.json and backlog.md only between runs. The orchestrator is the only writer of board.json while a session is active.
  • The old dashboard will not show the new panels until step 3 is done.
