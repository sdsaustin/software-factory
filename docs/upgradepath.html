Upgrade path

Moving a project that an older software-factory plugin set up (any version from 1.3.0) to the current version (1.8.x), and carrying on where you left off. In short: update the plugin, restart Claude Code, run /software-factory:init.

Why an upgrade does not break a project in progress

All state lives in your project, not in the plugin: factory/board.json, backlog.md, learnings.md, factory/jobs/<id>/…, docs/…, and the job branches in git. The plugin supplies the instructions (skills and agents) and three files it copies into factory/: dashboard.html, server.py and userguide.html. Every field added to board.json since 1.3.0 is optional, so an old board is valid as it stands. Old backlog lines such as - [ ] [E1] text keep working: they get positional ids and no dependencies.

From 1.8.0 the board records which plugin version last set the project up (plugin_version). Every factory command compares it with the plugin that is running and prints one line when they differ: run init to upgrade if the project is older, update your plugin if a teammate upgraded it with a newer one. It never blocks a command. Projects from before 1.8.0 have no stamp and get the same one-line reminder.

1. Update the plugin

  1. Open /plugin, go to Installed, and update software-factory. If no newer version is offered, update the marketplace first (Marketplaces in the same menu).
  2. Restart Claude Code (or run /reload-plugins). Skills load when a session starts.
  3. Optional check: 
    grep -A3 software-factory ~/.claude/plugins/installed_plugins.json
    The installPath ends in the new version. Old versions may stay in ~/.claude/plugins/cache/; init and the factory read the installed path, never the first folder a search finds, so they cannot pick up an old copy.

2. Run init in the project

/software-factory:init

On a project that already has factory/board.json, init runs as an upgrade:

  1. Version check. If the project was upgraded by a newer plugin than yours, it stops and asks you to update your plugin instead.
  2. Default branch. It needs your default branch checked out, since factory state is only committed there.
  3. One summary, one question. It lists what it would change: plugin-owned files that are missing or differ, fields missing from board.json, the backlog header and ids, and the diff of the ## Software factory section of CLAUDE.md. Answer yes, no, or yes with exceptions (“yes, but not CLAUDE.md”). If a run is marked running, or a job is in spec, build, review, triage or decision, the summary lists them and your yes must also confirm that no other Claude session is working in the project (a crashed session counts as not working). When there is nothing to change, it asks nothing beyond the merge-permission question, and that only if the rule is missing.
  4. Snapshot, then apply. Uncommitted factory state is committed first as factory: before upgrade to <version>, so one git revert undoes the upgrade. Then the changes are made.
  5. Dependencies (offer, see step 3) and the merge permission question, skipped if the rule is already there.
  6. Report. What changed, any backlog lines that look stuck, every job still waiting with the command that continues it, and an offer to commit factory: upgrade to <version>.
WhatUpgrade does

learnings.md, jobs/, docs/, inbox.*, followups.mdNever touched. Missing learnings.md or jobs/.gitkeep are created.

Running init again changes nothing; it says the project is up to date.

3. Dependencies in the backlog (the step that matters for a long backlog)

A backlog without depends: makes /factory run treat every item as independent. If item 12 is parked for a human and item 13 really needs it, the run would still build 13 on a base that does not exist. When no line has a dependency and two or more are open, init offers to propose them from docs/epics.md and docs/architecture.md, and adds them only after you agree. Read the list before accepting it:

  • Too few links is risky: a parked job will not stop items that need it.
  • Too many links is wasteful: one parked job then blocks everything after it. Independent items should not be chained.
  • Dependencies must point to earlier ids and must not form a cycle.
Do not re-run the planner for this. Product planning Pass 3 regenerates the backlog. If you skip the dependencies, use /software-factory:factory next one job at a time instead of run.

4. First run with the new features

  1. Start the dashboard. Stop any old server.py or python3 -m http.server first, then: 
    python3 factory/server.py
    Open the exact URL it prints, including the #t=… part; that token is what lets the page queue actions. It listens on 127.0.0.1 only and tries ports 8000 to 8020.
  2. Start small. Do not begin with all remaining items: 
    /software-factory:factory run --max-jobs 3
    Each job can spawn up to eight agent runs per round, so a full run is large. Watch the dashboard: the banner shows the run state, and parked jobs appear under Needs you.
  3. Answer parked jobs. Pick an option (the recommended one is highlighted) and submit. A click only queues the action. Then, in your Claude session: 
    /software-factory:factory apply
    Apply re-checks each action against the board, re-runs the tests from a clean copy of the branch before any merge, and records the result under Recent actions.
  4. Continue with /software-factory:factory run resume, or with a larger --max-jobs.

The run stops by itself when nothing is ready, when a limit is reached, when two jobs in a row are parked (usually one systemic problem), when the default branch fails its tests after a merge, or when your permission settings refuse a merge (MERGE BLOCKED; the merge rule init offers prevents it).

Between jobs (nothing in flight)/software-factory:factory next, or run to drain the rest.
A run that was stopped or crashed/software-factory:factory run resume (state is read from board.json run and the backlog).
Mid-job (stage spec, build, review, triage or decision, and no session working on it)/software-factory:factory rework <id> resume after interruption. A job still in spec gets its spec redone; a later stage goes back to the builder with a fresh review round. Every agent run starts clean from files, so redoing a step loses nothing.

Rollback

  1. Stop server.py and any session.
  2. Undo the upgrade commit: git revert <the "factory: upgrade to …" commit>. If you did not commit it, git checkout -- factory CLAUDE.md returns to the factory: before upgrade snapshot.
  3. Reinstall the older plugin version if you need the old behavior, then restart Claude Code. The factory will remind you that the project is newer than the plugin; that is expected after a rollback of the plugin only.
  4. Job branches and merges already made are ordinary git history; revert them with git if needed.

Manual upgrade (plugins before 1.8.0 only)

You only need this if you cannot install 1.8.0 or later; any later plugin upgrades a project of any older version through init. The manual route is: back up with cp -r factory factory.bak; copy dashboard.html, server.py and userguide.html from the plugin's templates/factory/ (take the folder from installPath in ~/.claude/plugins/installed_plugins.json, not from a find, which can return an old cached version); give backlog lines B<n> ids and dependencies by hand; re-run init for the merge-permission question.

Known gaps and risks

The upgrade was tested in a sandbox on hand-built projects from 1.3.0 and 1.7.0 and on one stamped by a newer plugin, run unattended. It was not tested on a real project with weeks of history. Start with --max-jobs 3 after upgrading and compare against your expectations.
  • Run isolation (a fresh sub-orchestrator per job), the stop after two parked jobs in a row, and the per-epic retro are not yet exercised (limitation L15 in the architecture document).
  • Dashboard clicks only queue actions; nothing happens until you run /factory apply (L13).
  • Edit board.json and backlog.md only between runs. The orchestrator is the only writer of board.json while a session is active; init writes it only after you confirm nothing is running.
  • Local edits to dashboard.html, server.py or userguide.html are replaced. Keep customisations elsewhere, or answer “yes, but not <file>”.
