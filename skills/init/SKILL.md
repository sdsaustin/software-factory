# Initialize or upgrade the software factory

Set up the factory in the CURRENT project (the user's working directory), using the templates shipped with this plugin.

**Plugin folder**: use `${CLAUDE_PLUGIN_ROOT}`. If it shows up unexpanded, read `installPath` of the `software-factory@...` entry in `~/.claude/plugins/installed_plugins.json`; only if that is missing, take the highest version from `find ~/.claude/plugins -type d -path '*software-factory*/templates'`. Never take the first `find` result: old cached versions sit beside the current one. The templates are in `<plugin>/templates`; the running version `V` is `version` in `<plugin>/.claude-plugin/plugin.json`.

**Mode**: if `factory/board.json` exists, the project is already initialized: follow **Upgrade** below and skip **Steps**. Otherwise follow **Steps**.

## Steps
1. **Git**: if the directory is not a git repo, run `git init -b main` and tell the user. Otherwise detect the default branch (`git symbolic-ref --short refs/remotes/origin/HEAD` without `origin/`, else the current branch). Keep whatever it is called (`master`, `develop`, `trunk`...); never rename a branch. After step 2, record it and the version with the state tool: `python3 factory/factoryctl.py set default_branch=<name> plugin_version=<V>` (the board is only ever changed through `factoryctl`). Warn if the current branch is not the default branch, or there are uncommitted changes outside `factory/`, `docs/` and `CLAUDE.md`, since jobs require both.
2. **Factory files**: create `factory/` and `factory/jobs/` (with an empty `.gitkeep`). Copy each file from `templates/factory/` (`board.json`, `backlog.md`, `learnings.md`, `config.json`, `events.jsonl`, `factoryctl.py`, `dashboard.html`, `server.py`, `userguide.html`) ONLY if it does not already exist. List which were created and which were skipped. Never overwrite; if a file exists and differs, say so and move on.
3. **CLAUDE.md**: if `CLAUDE.md` does not contain the marker `software-factory:project-context`, append `templates/project-context.md` to it (create the file if missing, separated by a blank line). If the marker is present, leave it alone.
4. **.gitignore**: ensure `.DS_Store` is listed; add nothing else here (step 6 may add `.claude/settings.local.json`). Do not ignore `factory/`; it is committed state.
5. **Detect the stack (existing code only)**: if the project already has source files, look for the test, lint and build commands (package.json scripts, Makefile, pyproject/tox, Cargo.toml, go.mod, CI config). Run the test command once to confirm it works. Then propose filling in the `Running the project` section of `CLAUDE.md`, show the exact lines, and apply them only after the user agrees. Record only non-obvious facts there, not tech-stack lists. If there is no code yet, skip this step.
6. **Merge permission (ask first)**: a `/factory run` merges each job the approver approves (`git merge --no-ff factory/<id>`). Claude Code's permission system, auto mode in particular, can refuse that merge as an action the human did not ask for, and the job then parks as `MERGE BLOCKED` until the human clicks approve. Explain this in two sentences and ASK whether to allow the factory's merges in this project. Only on a clear yes, add the rule `Bash(git merge --no-ff factory/*)` to `permissions.allow` in `.claude/settings.local.json` (personal, not committed; or `.claude/settings.json` if the user wants it shared with everyone who runs the factory in this repo). Read the file first if it exists and merge the rule into it: keep every other key and rule, never add a duplicate, and if the file is not valid JSON, change nothing and show the user the line to add. Create `.claude/` and the file if missing, and make sure `.claude/settings.local.json` is listed in `.gitignore`. The rule matches only merges of factory job branches; merges still happen only after an APPROVE and a passing verification. Tell the user it takes effect at once (Claude Code reloads its settings files; `/permissions` shows the rule and which file it came from), and that a `deny` or `ask` rule matching `git merge`, in any settings file, still wins. On no, say they can add it later with `/permissions` or by re-running init. If the rule is already present, say so and skip the question.
7. **Report and next step**: print a short summary of what was created. Then recommend ONE next step:
   - Empty project, only a vision/idea: `/software-factory:factory plan <your vision>`.
   - Existing project: confirm the test command in `CLAUDE.md`, run `/software-factory:factory document` so agents know the existing architecture and decisions, then `/software-factory:factory plan <capability>` to plan a capability into backlog items (feature mode), or `/software-factory:factory <feature>` for one change.
   Say that after every plugin update they should restart Claude Code and run `/software-factory:init` again to upgrade the project. Mention the dashboard: `python3 factory/server.py`, then open the exact URL it prints (the `#t=` part lets the page queue actions such as approve and rework; they are carried out by `/software-factory:factory apply`). It listens on 127.0.0.1 only. For view-only, `cd factory && python3 -m http.server 8000` still works. Also the guide at `factory/userguide.html`.
8. Offer to commit the new files (`git add factory CLAUDE.md .gitignore`, plus `.claude/settings.json` only if step 6 wrote the shared file). Commit only if the user says yes.

## Upgrade
For a project that a plugin version (this one or older) already initialized. Your state is never rewritten: `board.json` jobs (their stage, decision and every field they already have), `plan`, `features`, `document` and `run`, the backlog's item lines (except adding ids, step U5), `learnings.md`, `inbox.*`, `followups.md`, `events.jsonl`, the values in `config.json`, `jobs/` and `docs/` stay as they are. Plugin-owned files are refreshed: `factory/factoryctl.py`, `factory/dashboard.html`, `factory/server.py`, `factory/userguide.html`, the backlog header comment, and the `## Software factory` section of `CLAUDE.md`.

U1. **Versions**: `P` is `plugin_version` in `board.json` (missing means "before 1.8.0"). If `P` is newer than `V`, or the board's `version` is above 2, stop: someone upgraded this project with a newer plugin, so the user should update theirs (`/plugin`, then restart Claude Code) and change nothing here. Compare versions numerically, part by part.
U2. **In flight**: note whether `run.status` is `running` or any job is in `spec`, `build`, `verify`, `review`, `triage` or `decision` (the in-flight list; U4 asks about it, U9 reports it; the upgrade never touches these jobs). Check that the default branch (`default_branch` in `board.json`, else detect it as in step 1) is checked out; if not, stop and say so: factory state is only ever committed on the default branch.
U3. **Collect the changes** (write nothing yet):
   - Each of `factoryctl.py`, `dashboard.html`, `server.py`, `userguide.html`: `missing` (will be created), `same` (skip) or `differs` (will be replaced). Compare bytes with `cmp`. `learnings.md`, `backlog.md` or `jobs/.gitkeep` that are missing will be created from the templates.
   - `board.json`, `config.json`, `events.jsonl`: run the plugin's copy of the state tool as a dry run, `python3 <plugin>/templates/factory/factoryctl.py --dir factory migrate`. It lists what the migration would do (board version 1 -> 2 with defaults added to each job, never a changed stage or decision; config fields to add; files to create) and writes nothing. If it refuses (an unreadable or newer board), stop and show why. Also `default_branch` if missing (detect as in step 1), and `plugin_version` set to `V`. Nothing else in the board is added, removed or reordered.
   - `backlog.md`: whether its header comment (the `<!-- ... -->` line under `# Backlog`) differs from the template's; whether item lines (`- [ ] ` or `- [x] `) lack a `B<n>` id (see U5).
   - `CLAUDE.md`: if the marker `software-factory:project-context` is missing, the whole template block will be appended as in step 3. Otherwise compare its `## Software factory` section (from that heading to the next `## ` heading or the end of the file) with the template's; if it differs, show the diff. The other sections (Policy, Running the project, conventions, pitfalls) belong to the user and are never edited.
U4. **One confirmation**: show `P` -> `V` and the list from U3 in one short summary, and ask once to apply it. If the in-flight list is not empty, show it in the same message and make the question also ask the user to confirm that no other Claude session is working in this project right now (a crashed run counts as not working): the orchestrator may be writing `board.json`, so anything but a clear yes changes nothing. Say that a replaced file loses any local edits but stays in git history, and that a running `server.py` must be restarted to pick up the new one. The user may exclude items ("yes, but not CLAUDE.md"). If the list is empty apart from `plugin_version`, ask nothing: set `plugin_version` if it differs (`python3 factory/factoryctl.py set plugin_version=<V>`) (only when the in-flight list is empty; otherwise leave it for the next init), say the project is up to date, and go to U7 (skip U6: it is offered only in an init that applied changes). On no, change nothing and stop.
U5. **Apply**: first, if `git status --porcelain factory CLAUDE.md` shows changes, commit them as they are (`git add factory CLAUDE.md`, `git commit -m "factory: before upgrade to V"`), so one revert undoes the upgrade. Then copy the files with `cp` from the templates; if a copy is refused or fails, read the template and write the whole file with the Write tool, never patch the project's copy by hand, and confirm with `cmp` that it now matches. Then migrate with the project's (now current) copy: `python3 factory/factoryctl.py migrate --apply`, and record the rest with `python3 factory/factoryctl.py set plugin_version=<V>` (plus `default_branch=<name>` if it was missing); never edit `board.json` by hand. Replace the backlog header comment, and replace the `## Software factory` section in place (or append the block). Backlog ids: if NO item line has an id, number every item line `B1`, `B2`, ... in file order, inserting `B<n> ` right after the checkbox, changing no other character; this matches how the orchestrator already counts unnumbered lines. If some lines have ids and some do not, change nothing and list the unnumbered lines for the user to fix by hand.
U6. **Dependencies (offer)**: if no item line has a `depends:` and at least 2 are unchecked, explain in two sentences that `/factory run` then treats every item as independent and may build an item whose prerequisite is parked, and offer to propose dependencies. On yes, read `docs/epics.md` and `docs/architecture.md` if they exist, and propose `(depends: B<m>)` only where an item cannot be built or tested without an earlier one: never a later id, never a cycle, and never chain independent items. Show the list; append the tags to the lines only after the user agrees, changing no other wording or checkbox. Otherwise suggest `/factory next` instead of `run` until they add them.
U7. **Merge permission**: step 6, unchanged (it skips the question if the rule is already there).
U8. **Consistency checks (report only, never fix)**: a job with an `item` whose backlog line is `[x]` while the job is not `done` (older versions ticked lines when a job started), or, for a board whose jobs have no `item`, a count of `[x]` lines that differs from the count of `done` jobs. Also run `python3 factory/factoryctl.py doctor` (read-only) and include its FAIL and WARN lines with their fixes.
U9. **Report**: `P` -> `V`, what changed, what was skipped, the U8 findings, and every job left in flight with how to continue: a job in `needs-human` with `/software-factory:factory approve <id>` or `rework <id> <note>`; a stopped or crashed run with `/software-factory:factory run resume`; a plan in progress with `/software-factory:factory plan`; a job caught mid-stage (`spec` to `decision`, left behind by an interrupted session) with `/software-factory:factory rework <id> resume after interruption`, which restarts it from its files. Then offer to commit (`git add factory CLAUDE.md`, plus `.gitignore` and `.claude/settings.json` if they changed) with `factory: upgrade to V`; commit only on yes. Never start a job, run or planning pass.

## Rules
Idempotent: running init twice changes nothing the second time, and an upgrade run twice changes nothing the second time. Do not start any job or planning pass from init. Never write any permission rule other than the one in step 6, and never without the user's yes in this session.
